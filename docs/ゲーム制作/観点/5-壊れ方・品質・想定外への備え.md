# 5. 壊れ方・品質・想定外への備え

## 見方の説明

この見方は、ゲームがどう壊れるか、作り手が想定しない使われ方をされたとき何が起きるか、そして品質・安全・不正にどう備えるかを見る。QA(品質保証)にあたる見方である。面白さそのものではなく、面白さが壊れずに届くか、届いたあとも保たれるかを問う。ただし、この見方の根拠は、ゲーム開発の記事が薄く、大半がゲーム開発以外の職種の記事である(詳しくは「この見方の限界」)。

## 相談役が投げる問い

- 遊んでいる最中に絶対に止まってはいけない場面は、どこか。そこが止まると何が起きるか。
- 作り手が想定していない遊び方・操作・順序で触られたとき、何が起きてほしいか。起きてほしくないことは何か。
- 対象は、どの環境(機種、画面サイズ、音の出る環境、通信状態)で遊ばれるか。実際の環境で確かめる時期と手段はあるか。
- オンライン要素や、他人と競う要素はあるか。ある場合、ずるをする人が出たとき、他の人の楽しみはどう守るか。
- 酔いやすさ、色の見分けにくさなど、一部の人が遊べなくなる要因に、事前に配慮するか。
- 発売後や公開後に見つかった問題を、直して届ける手段はあるか。

## 根拠

### 任天堂の記事(出典つき)

- **記事 97「ゲームを健康体で送り出すために」** — https://www.nintendo.co.jp/jobs/keyword/97.html(職種: QAエンジニア。記事の職種欄は空で、本文の記述による。強さ: 中)
  - 要約: 運動と連動するゲームでは、処理落ちが起きると動きと画面がずれ、ゲームとして成り立たなくなる。そこで、コース上の多数の地点に自動でプレイヤーを移し、負荷を毎日測る仕組みを作り、新しい処理落ちに早く気づけるようにした。バグの確認は、外部のテスト担当と同じ建物で顔を合わせ、確定した仕様と調整中の仕様を伝えながら進めた。

- **記事 54「想定外のシナリオを用意して臨む」** — https://www.nintendo.co.jp/jobs/keyword/54.html(職種: 理工系(ネットワーク) / ネットワークサービス開発。ゲーム開発ではない。強さ: 弱)
  - 要約: 加入状況を判定するサーバーが止まるとオンラインで遊べなくなるため、サーバーは壊れるものと考え、予備を置き、アクセス数に応じて増減できる設計にした。負荷テストでは予測を超えるアクセスの場面も用意し、どこでどんな異常が起き、どう直すかを文書にした。サーバーという仕組みの話で、ゲームの中身への適用は読み手の判断になる。

- **記事 77「安心安全なネットワークサービスのために」** — https://www.nintendo.co.jp/jobs/keyword/77.html(職種: 理工系(ネットワーク) / ネットワークセキュリティ。ゲーム開発ではない。強さ: 弱)
  - 要約: 対戦での不正や、アイテムの複製などの改ざんは、他の遊び手の楽しみを奪う。発売前に、仕様を把握し、実際のプレイを模して弱点を調べる。発売後は、不正を早く見つけ、更新や利用停止で対応する。完全には防げないという前提で書かれている。

- **記事 35「ありえない使われ方も検証」** — https://www.nintendo.co.jp/jobs/keyword/35.html(職種: 電気回路設計(ハードウェア)。記事の職種欄は空で、本文の記述による。ゲーム開発ではない。強さ: 弱)
  - 要約: コントローラーの部品が同時に動いたり、想定より電力を使ったりすると不具合が出るため、各部品の消費電力を常に調べ、企画側の「この組み合わせは使えないか」という問いに、データを見て答えられるようにした。量産前の試作を各部署に配ると、それまで見つからなかった不具合が出ることもあったとされる。ハードの話で、ソフトにそのまま当てはまる記述ではない。

### 二次資料の複合結果(出典なし)

- 規模が大きいと、キャラ・技・アイテム・地形などの組み合わせが膨大になり、総当たりの確認はできない。そのため、強制的に相手を制御する処理、場面の切り替え、無理な地形、成長要素など、不具合が出やすい場所を狙って確かめるとされる。(強さ: 中)
- 不具合は再現手順を付けて管理し、重要度で順位を付ける(止まる、保存データが壊れる、は最上位)。直したあとは複数の条件で確認し、一つ直すと別の不具合が出うるため、早く見つけて早く直す体制が要る。(強さ: 中)
- 広い世界や多様なゲームでは、機械に一晩自動で遊ばせて不具合を探す手が使われる。(強さ: 弱)
- 開発中に使う確認用の機能(体力の指定、画面の静止、カメラの自由移動など)は、確認の手間を減らす。製品版では外すのが一般的とされる。(強さ: 弱)
- 開発用の機材と製品の実機では処理速度が違い、難易度やテンポが変わることがある。最適化や実機への移行のあとは、実機で確かめ直すとされる。実機で試すのが遅いと、想定外の仕様が残る。(強さ: 中)
- 発売後の市場での試行回数は、開発中のデバッグを大きく上回り、条件により、ごくまれな不具合も見つかる。そのため、致命的な不具合を直す更新は避けにくいとされる。バランス調整は、不具合修正とは別の、任意の改善として扱われる。(強さ: 中)
- ゲーム内でできるずる(自滅の利用、繰り返しの稼ぎなど)は、すべて潰さず、許容したほうが印象に残るという考え方がある。ただし、他人に損害を与える不正は別の問題として扱われているわけではなく、資料には明確な区別が書かれていない。(強さ: 弱)
- アクセシビリティ(色の見分けにくさへの対応、高コントラスト、画面表示の大きさ変更、酔い対策としてのカメラ揺れの抑制)を手厚くする例が挙げられ、大作では望ましいとされる。(強さ: 弱)
- 文字の大きさや音の聞こえ方は、実際の機器・環境(携帯モード、小さなテレビのスピーカーなど)で確かめるとされる。作り手の環境だけで仕上げると、客の環境で崩れる。(強さ: 中)
- 処理負荷を抑えるため、想定どおりのバランスにならず、不具合が残ったまま出した、という反省も挙げられている。(強さ: 弱)

## 失敗の兆候

- 実際に遊ばれる環境(機種、音、画面、通信)で、一度も確かめられていない。
- 「普通は、こう遊ぶはず」という前提だけで作られ、想定外の操作や順序の確認がない。
- 不具合の報告に、再現手順や重要度がなく、直したあとに別の不具合が出ても気づけない。
- オンライン要素や競う要素があるのに、不正への備えと、見つけたあとの対応が決まっていない。
- 処理落ちや負荷の測定が、問題が出てから初めて行われる。
- 一部の人(酔いやすい人、色の見分けにくい人)が遊べなくなる点が、検討されていない。

## この見方の限界

- 根拠の薄さ。ゲーム開発の記事は 97 の1本だけで、安全・不正への備えについては、根拠の大半がゲーム開発以外の記事(54 はサーバー、77 はネットワークセキュリティ、35 はハードの回路)である。二次資料でも、安全・不正の話はほとんどなく、確認、実機での検証、アクセシビリティが中心である。したがって、「不正・安全への備え」の部分は、資料からの裏付けが弱い。
- ジャンル・規模の偏り。記事は、大きな組織(専任のQA、外部のテスト担当、サーバーの専門職)の話が中心である。二次資料も、大規模な対戦ゲームの話が多い。個人や小規模のチームでは、専任の検証や自動化が現実的でないことが多く、資料がその場合の優先順位を示しているわけではない。
- 資料の原則どうしの食い違い。「不具合は可能な限りなくす」(記事 97)と、ゲーム内のずるはすべて潰さず許容してよい(二次資料)は、向きが逆である。また、不正は「完全には防げない」と書かれる一方、事前対策に力を入れる記述もある。どこまで備えるかは、ゲームの性質(対戦か一人用か、オンラインか)により、資料は判断の基準を与えていない。
- 数値や頻度(何回の試験で足りる、どの程度の負荷を見込む)は、記事ごとの状況の数字であり、他のゲームに移せる基準ではない。
