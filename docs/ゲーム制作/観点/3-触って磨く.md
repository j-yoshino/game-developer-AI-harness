# 3. 触って磨く

## 見方の説明

操作の手触りは、頭の中で決めきれない。作って、触って、直す。この往復の回数が、仕上がりの深さを決める。数値を外に出して、変更をすぐ実行中のゲームに反映できるようにすると、試す回数を増やせる。依頼や仕様を読むときは、「いつ・誰が・何を触って確かめるか」が書かれているかを見る。

## 相談役が投げる問い

- 最初に触れる状態になるまで、どのくらい作るつもりか。紙の上の仕様だけで進める部分はどこか。
- 手触りを決める数値(速度、慣性、ジャンプの高さなど)は、コードの外で変えられるか。変えてから確かめるまでに、何秒かかるか。
- 触って確かめる人は誰か。作った本人だけか。ゲームに慣れていない人にも触らせる予定はあるか。
- 触ったとき、何が気持ちよければ合格か。それを見る基準を、言葉で書けているか。
- 見た目、音、動きは、操作と一緒に確かめられるか。それとも別々の段階で作るか。
- 実機や実際の環境で試せるのは、いつか。それまでに確かめられないことは何か。

## 根拠

### 任天堂の記事(出典つき)

- **記事 173「実体験をもとに操作を磨きこむ」** — https://www.nintendo.co.jp/jobs/keyword/173.html(職種: 記載なし。本文ではプログラマーの語り。強さ: 強)
  - 要約: 操作の挙動を担当した語り手は、実物の車いすに乗って体を動かし、その実感をもとに動きを作った。速度に応じた前傾の角度などを、何度も試しながら詰めている。デザイナーやサウンド担当との相談で、動きと音が操作の強弱に連動する形になった。
- **記事 149「遊びと向き合い、デザインする」** — https://www.nintendo.co.jp/jobs/keyword/149.html(職種: 記載なし。本文ではキャラクターデザイナーの語り。強さ: 強)
  - 要約: 敵キャラクターを実際に動かして遊んでみたところ、脚が細すぎて当てにくく、遊ぶ人のストレスになると分かった。そこで脚を太くし、動きの調整もした。見た目の案のまま確定せず、遊んで直すことを繰り返したと述べている。
- **記事 161「作って、走って、また作る」** — https://www.nintendo.co.jp/jobs/keyword/161.html(職種: 記載なし。本文ではプランナーの語り。強さ: 中)
  - 要約: プランナーが自分で地形を作り、その上を何度も走って、形状、道の見やすさ、減速地帯やジャンプの置き方を確かめた。語り手は、手を動かしながら考えることの大切さを学んだと述べている。対象はレースゲームの地形で、操作の手触りそのものの調整ではない。
- **記事 106「より早く開発サイクルを回すために」** — https://www.nintendo.co.jp/jobs/keyword/106.html(職種: 記載なし。本文ではソフトウェアエンジニアの語り。強さ: 弱)
  - 要約: パソコン上で作ったプログラムを開発機に移さないと、ゲームの触り心地を確かめられない。データ量が多く待ち時間が開発の効率に響くため、必要な一部だけを送る機能を作り、確認を速くした。ゲーム制作者ではなくツール開発者の語りで、調整数値の話ではない。

### 二次資料の複合結果(出典なし)

- 調整したい数値をプログラムに直書きせず、外に出して管理するとよいとされる。仕組みは骨格(プログラム)と筋肉(数値)にたとえられる。(強)
- 数値の変更をボタン1つで動作中のゲームに反映できると、試行錯誤の回数が増え、調整が深くなるとされる。反映に時間がかかる環境では、この回数が減る。(強)
- 同じボタン操作でも、移動速度、慣性、ジャンプの仕様、フレームレートで、軽さや重さの感じが変わるとされる。手触りは仕様と調整の組み合わせで作る。(中)
- ジャンプなどの動きは、ゲームの目的に合わせて性格を変える。数値の大きさだけでなく、上昇と下降の速さの差のような形も調整の対象になる。(中)
- 実機に移ると処理速度が変わり、難易度や手触りが変わることがある。移行後は実機で確かめ直すべきだとされる。実機で試せる時期が遅いと、想定外のストレスが出た例が挙がっている。(中)
- 調整のために、体力の指定や画面の静止などを行う開発用モードを用意するとよいとされる。(中)
- 手触りの調整は、強すぎるところを削るだけだと全体が似通い、平凡になるという指摘がある。直すなら、威力は残して、発生や後隙など別の軸で調整するとされる。(弱。ジャンル固有の話で、一般化はできない)

## 失敗の兆候

- 仕様に「気持ちよく動く」とだけあり、速度や反応の目安も、確かめる方法も書かれていない。
- 触れる状態になるのが、計画の終盤に置かれている。それまでの工程が、紙と見た目だけで進む。
- 手触りに関わる数値の変更に、再ビルドや再起動が必要で、1回の確認に長い時間がかかる。
- 触って確かめる人が、作った本人だけである。ゲームに慣れていない人の手を通っていない。
- 見た目、音、操作が別々の担当と別々の時期で作られ、一緒に確かめる機会がない。

## この見方の限界

- 任天堂の記事は、語り手が自分の担当を振り返った体験談である。他の作り方と比べて効果が高いとは、記事からは言えない。
- 記事は、動きや触り心地が主役の大作と、専門の担当者が揃う大きなチームの話に偏る。個人や小規模のチームでは、同じ体制を取れない。
- 数値を外に出す仕組みは、二次資料の複合結果にしか根拠がない。任天堂の記事で直接これを述べるものは、ここでは見つからなかった。記事 106 は、確認を速くするツールの話にとどまる。
- 二次資料の複合結果は、対戦アクションの制作経験から出ている部分が大きい。パズル、物語中心、非リアルタイムのゲームには、そのまま当てはまらない。
- 資料の原則どうしの食い違いがある。何度も直して試す姿勢と、迷っても方針を曲げない姿勢は、並べて読むと緊張する。どこまで試して直し、どこから方針として固定するかは、資料からは決まらない。
