実装フロー

このリポジトリで、機能を実際に実装していくときの流れ。計画と実装は spec-kit を正本にし、superpowers は要件の掘り起こしとテスト・デバッグ・レビューに使う。

この文書について。通して実行して検証したものではない。手順 3・6 の任意のスキルと、/speckit-converge の置き場所は、各スキルの説明文を読んだうえで決めた(各手順に「出典」を付けた)。プロジェクトによって、流れは変わりうる。

0. 最初に1回だけ

やること内容
プロジェクトの原則/speckit-constitution で、プロジェクトの憲章を作る。.specify/memory/constitution.md は、テンプレートのままで未記入。
スキャンスキルやプラグインを取り込む前に、skillspector scan <対象> --recursive --no-llm。検出は、docs 内の記述か実行されるスクリプトかを確かめてから判断する。
新しいセッションプラグインの追加や設定の変更は、新しいセッションで反映される。

窓口: 最初の分かれ道

ユーザーの発言は、まず窓口(.claude/rules/window.md)を通る。毎ターン、フックが短い注意を届ける。遵守は保証されないため、新しいセッションで挙動を確かめる。

層条件呼び出すスキル
質問(層は判定しない)作業を求めない。何も変わらないwindow-question
軽作業取り返しがつき、小さく、spec に残すほどではないsuperpowers:brainstorming(規模を測る)→ systematic-debugging、test-driven-development、verification-before-completion
本件取り返しがつかない、外向き、または設計に及ぶ。新規実装superpowers:brainstorming → /speckit-specify → 以降は「3. 本件の流れ」

迷ったら重い層を選び、層は下げない。push・PR 作成・マージのような外向きの操作は、本件として先に確認する。納品書は「確認待ち」で報告し、完了とは言わない。承認はユーザーが行う。

1. 質問の流れ

作業を求めず、何も変わらない発言。層は判定せず、手続きは最小。

答える必須
呼び出すスキルwindow-question
やること答えから書く。根拠は path:line・URL・コマンドの出力で示す。事実でないものは、事実でないと明示する。
出さないもの層の判定、依頼票、納品書、層の宣言
作業が要ると分かったとき任意
やること作業の依頼として扱い、ユーザーに伝える。その時点で、軽作業か本件かを判定し、その流れに進む。

2. 軽作業の流れ

取り返しがつき、小さく、spec に残すほどではない変更(不具合修正など)。メインの会話が作業する。

規模を測る必須
呼び出すスキルsuperpowers:brainstorming
やること作業の大きさを測り、足りない点だけを聞く。設計メモは書かず、writing-plans には進まない。
作業する必須
呼び出すスキルsystematic-debugging(不具合)、test-driven-development(テストが当てはまるとき)
完了前に確かめる必須
呼び出すスキルsuperpowers:verification-before-completion
やること検証コマンドを実行し、出力を確認してから、完了と言う。
納品書を書く必須
成果物docs/納品書/<YYYY-MM-DD>-<題名>.md(docs/納品書/_template.md から)
やること確認した項目ごとに、何をしたか・確認した方法・確認していないことを書く。「確認待ち」と報告し、完了とは言わない。承認はユーザーが行う。

3. 本件(新規実装)の流れ

各手順を開くと、使うスキルと成果物が見える。

要件を決める必須
呼び出すスキルsuperpowers:brainstorming
やること何を作るかを決める。曖昧な点は聞かれる。設計メモ(design doc)を作る。
成果物design doc(次の手順にパスを渡す)
仕様を書く必須
呼び出すスキル/speckit-specify <design doc のパス>
やること自然言語の説明から、機能の仕様(spec.md)を作る。
出典speckit-specify の説明
仕様の曖昧さを潰す任意
呼び出すスキル/speckit-clarify
やること仕様の不足を、最大5問の質問で洗い出し、答えを仕様に書き戻す。
出典speckit-clarify の説明。置き場所(specify の直後)は補足。
計画を書く必須
呼び出すスキル/speckit-plan
成果物specs/<NNN-feature>/plan.md。計画書の正本はここだけ。docs/superpowers/plans/ は使わない。
使わないsuperpowers:writing-plans
タスクに分ける必須
呼び出すスキル/speckit-tasks
成果物依存関係の順に並んだ tasks.md
出典speckit-tasks の説明
実装の前に整合性を見る任意
呼び出すスキル/speckit-analyze(/speckit-checklist で、要件の品質チェックリストも作れる)
やることspec.md・plan.md・tasks.md のあいだの食い違いを、ファイルを変えずに調べる。
出典speckit-analyze / speckit-checklist の説明。置き場所(tasks の後)は補足。
実装する必須
呼び出すスキル/speckit-implement
実装中に併用 superpowers:test-driven-development(テストを先に)、 superpowers:systematic-debugging(不具合の原因を系統立てて調べる)、 superpowers:using-git-worktrees(作業の分離)
使わないsuperpowers:executing-plans、superpowers:subagent-driven-development。曖昧さを判断して進める仕組みが、answer-policy と食い違うため。
ルール該当の言語やエンジンのファイルを開くと、.claude/rules/<言語>/ が自動で読み込まれる(下の表)。
完了前に確かめる必須
呼び出すスキルsuperpowers:verification-before-completion、superpowers:requesting-code-review(指摘を受けたら superpowers:receiving-code-review)
未実装が残ったとき/speckit-converge で、コードを仕様・計画・タスクと照らし、残りを tasks.md に追記する。そのあと /speckit-implement に戻る。
出典converge の置き場所は補足。
ブランチを出して PR にする必須
ブランチdevelop から作業ブランチを切る。
PRdevelop 向けに作る。
禁止main に直接コミットしない。

4. 常に守ること(回答ポリシー)

やる

  • 確認できた事実は、言い切る。
  • 事実でないことは、事実でないと書く。
  • 検証は自分の側で完結させる。
  • ユーザーの手が要ることだけを「やり残し」に挙げる。
  • 曖昧なら AskUserQuestion で聞く。答えに曖昧さが残るなら、もう一度聞く。

やらない

  • 「読んだところ」のような、確認の経緯を書く。
  • 「動くはず」を事実として書く。
  • 自分で検証できたのに、ユーザーに渡す。
  • 曖昧さが残ったまま、判断して進める。

出典: .claude/rules/answer-policy.md

5. 言語・エンジン別のルール

ディレクトリ読み込まれる条件(paths)優先
cpp/C / C++ のソース・ヘッダ
csharp/**/*.cs
rust/**/*.rs、**/Cargo.toml
unity/Assets/**/*.csUnity では unity/ を優先
unreal-engine/Source/**、Plugins/**/Source/** の .h .cpp .csUnreal では unreal-engine/ を優先

コードを書くときの共通規則:新しいソースファイルは、先頭に Doxygen 形式のヘッダー(@file・@brief・@date・@author)を書く。コメント行の末尾には、ピリオドを付ける。
