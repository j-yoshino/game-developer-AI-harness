# 窓口の設計

お客様モデル(`docs/ハーネス設計/お客様モデル_役所の手続きとトヨタの自工程完結.md`)の「窓口」を、このハーネスに実装するための設計。

- 状態: 草案(ユーザーの承認前。builder 確認は済み)
- 作成日: 2026-11-15
- 範囲: 窓口のみ。「確かめる者」と引き継ぎ票は、別の設計とする(非目標を参照)。

## 1. 意図と、その理由

### 意図
ユーザーのどの発言にも、窓口を通す。窓口は、依頼の重さを判定し、種別ごとの手続きに回し、依頼と結果を照合し、納品書を書く。

### 理由(現状の穴)
- 今の流れ(brainstorming 以下)は、新規実装だけを扱う。不具合修正、spec に残さない小さな変更、ただの質問には、通る経路がない。
- 窓口の役、依頼票・納品書の書式、手続きの重さの判定は、リポジトリのどこにもない。
- answer-policy は散文の規約で、遵守は書く側の裁量に依存する(お客様モデルの 3-5)。

## 2. 目標・非目標・アンチゴール

### 目標
1. ユーザーのどの発言にも、窓口が最初に動く。
2. 作業を求める発言を、軽作業・本件の二つに判定する。質問(作業を求めない発言)には、層を付けない。
3. 質問は、専用スキル(`window-question`)が呼ばれて答える。
4. 軽作業と本件は、brainstorming で聞き取り、規模を伝える。
5. 新規実装は、spec の必須欄を依頼票として使う。
6. 作業の完了後、納品書を `docs/納品書/` にファイルで残し、ユーザーが確認する。

### 非目標(この設計では扱わない)
- 「確かめる者」の独立した役。別の設計で扱う。
- 引き継ぎ票。当面使わない。
- 言語・エンジン別のレビュー用エージェントの組み込み。
- メインの会話を窓口エージェントとして動かす方法(後述の案 B)。第1版では採らない。

### アンチゴール(技術的に動いても失敗とみなすもの)
- 質問のたびに、依頼票や層の宣言が出て、会話が重くなる。
- 軽作業のたびに、大きな設計メモが作られる。
- 窓口が、作られたものの正しさまで判定し、2つ目の検査役になる(お客様モデル 4 節)。
- 判定を誤ったと分かったとき、層を下げる。

## 3. 制約(確認できた事実)

出典は、いずれも公式ドキュメント(https://code.claude.com/docs/en/ 以下の memory、hooks、sub-agents、skills、settings)。

- 常時読み込みの rules、フックの `additionalContext`、skill、output style は、いずれも「モデルが従う文脈」で、遵守は保証されない。
- UserPromptSubmit フックは毎ターン発火し、`hookSpecificOutput.additionalContext` で文脈を確実に届けられる。`additionalContext` は 10,000 文字で打ち切られる。プロンプトの書き換えは、文書化されていない。
- UserPromptSubmit は、バックグラウンド完了通知などの自律的なターンでも発火する。ユーザー発言との区別方法は、未検証。
- UserPromptSubmit と `additionalContext` の最低バージョンは、未記載(未検証)。インストール済みは Claude Code 2.1.233。
- `paths` を持たない rules は、毎セッション読み込まれる。目安は 200 行未満。
- superpowers はプラグインのスキルで、`skillOverrides` は効かない。vendor 配下のファイルは、このリポジトリでは編集しない(submodule)。
- rules は英語で書き、日本語訳を `docs/rules-ja/` に置く(AGENTS.md の方針)。

## 4. 検討した案

### 4-1. 窓口をどう動かすか
| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A(採用)** | rules に手順を書き、UserPromptSubmit フックが毎ターン短い注意を注入する | 毎ターン確実に届く。今の Claude Code の指示を壊さない | 従うかはモデル任せ。分類はモデルが行う。2.1.233 での動作は未確認 |
| B | メインの会話を窓口エージェントにする(`--agent` / `agent` 設定) | 役が定義として固定される | 標準のシステムプロンプトを置き換える。`skills` の挙動と最低バージョンが未検証 |
| C | rules だけ | 最も軽い | 毎ターンの保証がない |

### 4-2. 新規実装での依頼票と brainstorming・spec-kit の関係(ユーザーが 2 を選択)
1. 依頼票を前に置く。二度手間になる。
2. **(採用)** brainstorming と spec を依頼票の役にする。窓口は、足りない欄だけ聞く。
3. 窓口は判定と最後の照合だけにする。依頼票の書式による守りが弱くなる。

### 4-3. 納品書の置き場所(ユーザーが `docs/` 以下を指定)
`specs/<NNN-feature>/` 配下、`spec.md` への追記、PR の説明文を検討した。ユーザーが確認するものなので、`docs/納品書/` に置く。

### 4-4. 軽作業の納品書(ユーザーが 2 を選択)
会話内の報告、ファイル、大きさで分ける案を検討した。軽作業も `docs/納品書/` にファイルで残す。

## 5. 設計

### 5-1. 窓口の動き
```
ユーザーの発言
  ↓ (毎ターン、フックが注意を注入)
作業を求めない発言(質問)→ 質問スキルが答える(層の判定なし。依頼票・納品書なし。根拠は path:line・URL・コマンド出力で示す)
作業を求める発言 → 窓口が判定: 軽作業 / 本件   ※層は上げるだけ。下げない
  ├─ 軽作業 → brainstorming が聞き取り、規模を伝える(設計メモ・計画には進まない)
  │           → メインの会話が superpowers のスキルで作業する
  │             (systematic-debugging / test-driven-development / verification-before-completion など)
  │           → 納品書を書く
  └─ 本件   → brainstorming → /speckit-specify(spec の必須欄 = 依頼票)
              → plan → tasks → implement → 納品書
```

### 5-2. 判定
二つの軸で判定する(お客様モデル 4 節)。
- 取り返しがつくか(外に出る操作を含むか)。
- 判断の分岐があるか。

| 層 | 条件 |
|---|---|
| 軽作業 | 取り返しがつき、spec に残さない程度の変更(不具合修正、小さな変更) |
| 本件 | 取り返しがつかない、または分岐が設計に及ぶ。新規実装 |

作業中に、取り返しのつかない操作が必要だと分かったら、その時点で本件に上げる。

### 5-3. 依頼票(新規実装)
`spec.md` の必須欄として、次を足す。

| 欄 | 内容 |
|---|---|
| ご要望 | ユーザーの言葉を、そのまま引用する(要約しない) |
| こう理解した | 言い換え |
| 誰のためか | 誰が読む・使う・判断するか |
| やらないこと | 線引き |
| 完了の判定 | 検収基準。納品書の各行に対応する |

窓口は、brainstorming と spec で埋まらなかった欄だけを、`AskUserQuestion` で聞く(選択肢の形)。ユーザーが spec に合意した時点が、依頼票の確定である。

### 5-4. 納品書
- 置き場所: `docs/納品書/`。
  - 新規実装: `docs/納品書/<NNN-feature>.md`(`specs/<NNN-feature>/` と名前を揃える)。
  - 軽作業: `docs/納品書/<YYYY-MM-DD>-<題名>.md`。
- 内容: 依頼票の「完了の判定」の各行(軽作業は、brainstorming で確認した「こう理解した」と「やらないこと」)に対して、次の三つを埋める。
  - 何をしたか
  - 確認した方法
  - 確認していないこと(核心の欄。空欄にしない)
- 依頼に無い項目を足したときは、足したことを明示する。
- 言語は日本語(ユーザーが確認するもの)。

### 5-5. 作るもの
| 成果物 | 内容 |
|---|---|
| `.claude/rules/window.md`(英語) | 窓口の手順の本体。`paths` を付けず常時読み込ませる。200 行未満 |
| `docs/rules-ja/window.md` | 上の日本語訳 |
| フックのスクリプトと `.claude/settings.local.json` の `hooks` | 毎ターン、窓口の注意を `additionalContext` で注入する |
| 質問スキル(`.claude/skills/` 配下) | 質問への回答の手順。根拠を path:line・URL・コマンド出力で示させる(answer-policy と同じ扱い) |
| spec テンプレートの変更(`.specify/templates/spec-template.md`) | 5-3 の必須欄を追加する |
| 納品書のテンプレート(`docs/納品書/`) | 5-4 の書式 |
| `AGENTS.md` の更新 | 窓口の説明と、flow の位置づけ |

### 5-6. 検証の方針
- 遵守は保証されないため、実際の挙動で確かめる。新しいセッションで、質問・軽作業・本件の例を、それぞれ入力する。
- 確認する点: 判定が出る、質問に依頼票が出ない、軽作業で納品書ができる、本件で spec の必須欄が埋まる。
- 失敗した場合の扱い: 注意文を直す。それでも従わないなら、案 B への移行を検討する。

## 6. ユーザーの決定(builder 確認で出た質問への回答)
- **作る者の分離**: 軽作業は、メインの会話が superpowers のスキルで作業し、納品書だけを足す。第1版では、軽作業も本件も、作った者が納品書を書く(「確認していないこと」は自己申告。独立した確認は「確かめる者」の設計で扱う)。理由: 軽作業は spec に残さない程度の変更で、superpowers のスキルで作業の質が足りる。足りないのは、作業後の報告の書式(納品書)だけ。
- **質問の判定**: 不要。質問(作業を求めない発言)は、層を判定せず、質問スキルが呼ばれる想定。窓口が判定するのは、作業の依頼(軽作業・本件)だけ。(「質問の判定は不要でスキル呼び出しされる想定で」)
- **質問の回答**: 「確認した方法」を、証拠を示す意味に狭める。「読んだ」のような経緯は書かず、path:line・URL・コマンド出力を示す。answer-policy は変更しない。事実でないものを明示する点も、今までどおり。

## 7. このドキュメントでの私の判断(ユーザーが決めていないもの)
- 軽作業の納品書のファイル名: `<YYYY-MM-DD>-<題名>.md`。フォルダー名: `docs/納品書/`。
- 質問スキルを、専用のスキルとして切り出す(ユーザーの指示は「別でスキル欲しい」)。名前は builder に任せる。
- 判定の宣言: 質問には層がないため出さない。軽作業以上は、brainstorming の「規模を伝える」で出す(ユーザーの回答から読み取った。確認は未了)。
- フックの設定は `.claude/settings.local.json`(このリポジトリは、このファイルをコミットする運用)。スクリプトは `.claude/hooks/` に置く。
- 軽作業の brainstorming: 窓口の rules に、設計メモを大きく作らず、聞き取りと規模の伝達にとどめる、と書く。従うかはモデル任せ。
- 軽作業の作業の進め方: メインの会話が、必要に応じて systematic-debugging、test-driven-development、verification-before-completion を使う。brainstorming は規模の判定にとどめ、`writing-plans` には進まない(AGENTS.md の方針)。窓口の rules に書く。
- 納品書の確認: 納品書に状態欄(確認待ち・承認済み)を持たせる。置いたら「確認待ち」と報告し、完了とは言わない。承認は、ユーザーが行う。
- spec テンプレート: 既存の欄は残し、先頭に「依頼票」の節を足す。spec-kit の更新で上書きされうるため、更新後に差分を確認する。
- 境界の既定: 迷ったら層を上げる。ローカルの commit、ドキュメントだけの変更、rules や設定の編集は軽作業。push、PR 作成、マージは外向きの操作で、本件の確認を取る。
- フックの注入文: 質問でも毎ターン届くため、トークン量も含めて短くする(数行)。
