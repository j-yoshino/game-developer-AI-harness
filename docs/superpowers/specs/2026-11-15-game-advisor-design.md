# 相談役(ゲーム制作の第三者)の設計

このハーネスに、「ゲーム制作脳」を持たせるための、最初の設計。仕様を詰めるときと、実装を変えるときに、作る側とは別の目で、助言・QA をする役(相談役)を置く。

- 状態: 草案(ユーザーの承認前)
- 作成日: 2026-11-15
- 範囲: 相談役の仕組みと、最初の小さな知識(種)。知識の全量の収集は、別の仕事(8 節)。

## 1. 意図と、その理由

### 意図
抽象的な依頼を、使いやすさ(ユーザビリティ)が極めて高いゲームになる方向に、意図を汲んで解釈し、解釈案を出す第三者を置く。ユーザーは、その案に合意してから進み、作ってみて違えば、検収で、補われた点を1点ずつ覆せる。

### 理由
- ユーザーは、考えがまだ抽象的で、ハーネスに、ゲーム制作の考え方を持たせたい。
- いまのハーネスは、コードの規約と作業の手続き(窓口、spec-kit、検査)を持つが、「何を面白さとするか」「どう試して磨くか」といった、ゲーム制作そのものの考え方を持たない(リポジトリを検索して確認した)。
- 面白さのような、採点が主観的で曖昧な判断ほど、独立した評価役が効く(Anthropic の見解。https://www.anthropic.com/engineering/harness-design-long-running-apps)。

## 2. 目標・非目標・アンチゴール

### 目標
1. 抽象的な依頼のとき、相談役が、6つの見方(下の 5-2)で、解釈案と、補った点(番号付き)を返す。
2. ユーザーが、解釈案に合意してから、仕様・実装に進む。
3. 合意した補った点を、依頼票に記録し、納品書で1点ずつ確認でき、検収で覆せる。
4. 相談役の見方の根拠を、任天堂の記事の要約(出典付き)として、`docs/` にファイルで持つ。

### 非目標
- 相談役が、決めて、進むこと。ユーザーは、「提案して、合意を取る」と「検収で覆せる」を選び、「相談役が決めて進む」を選ばなかった。
- `answer-policy` と窓口の規則(聞く、合意するまで進まない)の変更。
- 知識の全量の収集(139 本の記事と、YouTube)。別の仕事とする(8 節)。
- 作った後の検査。それは、確かめる者の役である。
- 記事の全文の転記。

### アンチゴール(動いても失敗とみなすもの)
- 相談役が、「遊びを面白く」のような、一般論だけを返し、根拠(出典)がない。
- 相談役が、決めて、進める(合意を飛ばす)。
- どの依頼でも、相談役が呼ばれ、小さな変更や、原因が明らかな不具合の修正まで、重くなる。
- 相談役が、窓口の「2つ目の窓口」になる(依頼の照合を始める)。
- 記事の本文が、そのまま、リポジトリに入る。

## 3. 制約(確認できた事実)

- サブエージェントは、会話の履歴を見られない。見えるのは、委任メッセージと、`CLAUDE.md`・`AGENTS.md`・`answer-policy.md` だけ。`paths` 付きの rules と、窓口のフックの注入文は届かない(2026-11-15、実機で確認)。
- `vendor/` は編集しない。brainstorming は、vendor のスキルで、編集できない。呼び出しは、窓口の規則(`.claude/rules/window.md`)に書く。従うかは保証されない。
- カスタムエージェントは、`.claude/agents/` に作ると、同じセッションの利用可能なエージェントの一覧に出る(`window-verifier` などで確認)。
- 任天堂の「仕事を読み解くキーワード」は、記事 139 本(2026-11-15 時点)。記事は静的なページで、1本あたり約 1,500 字。各記事は、社員の一人称の体験談で、「インタビュー当時の情報に基づく」と注記がある。https://www.nintendo.co.jp/jobs/keyword/index.html
- 本文を読んだ記事: 52(「遊びの核をはっきりさせる」)、51(「遊んでくださる人のことを第一に」)。その他は、題名だけ。
- 通読(2026-11-15、139 本)の結果は、`docs/ゲーム制作/観点の検証メモ.md`。当初の見方 5(想定外の遊ばれ方)は、ゲームの遊ばれ方としての根拠が乏しかった。
- YouTube(桜井政博さんのチャンネル)は、まだ読んでいない。
- 著作物のため、全文は転記せず、出典付きの要約にする。引用は、短く、必要なものだけ。

## 4. 検討した案

### 4-1. 相談役を、どう作るか(ユーザーが案 A を選択)
| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A(採用)** | 別の文脈で動くエージェント(`game-advisor`)。知識は `docs/` にファイルで置き、相談役が読む。brainstorming の途中で、メインが呼ぶ | 独立した第三者。確かめる者と同じ作りで、一貫する | 呼ぶ指示は窓口の規則で、従うかは保証されない。委任メッセージの書き方に気を使う |
| B | 同じ会話の中で使うスキル | 安い。会話全体を見られる | 独立した第三者ではない。作る側と同じ盲点を持つ |
| C | 見方を rules に書くだけ | 最も軽い | 受け身で、自分から批評しない |

### 4-2. 相談役の自律の度合い(ユーザーが、1 と 2 の間を選択)
| 案 | 内容 |
|---|---|
| 1 | 提案して、合意を取る |
| 2 | 取り返しがつく範囲は、相談役が決めて進み、決めた点を記録して、検収で覆せる |
| **採用** | 1 と 2 の間: **提案して合意を取る**。**検収で、補った点を1点ずつ覆せる**。「相談役が決めて進む」は、採らない |

理由(ユーザーの言葉): 作ってみて、触ってみて、目指しているものとイメージがズレる、違うと思うことがあるため。

### 4-3. 順序(ユーザーが選択)
仕組みを先に作り、見方に合う十数本の記事で、小さく始める。その後、全量(139 本)を集めて広げる。

## 5. 設計

### 5-1. 流れ
```
抽象的な依頼 → 窓口 → 本件(または軽作業) → brainstorming(聞き取り)
  → 解釈が要るとき、メインが game-advisor を呼ぶ
       委任メッセージ: ユーザーの原文、聞き取りで分かったこと(原文と区別して書く)
  → game-advisor が、知識(docs/ゲーム制作/)を読み、返す:
       解釈案(1〜3案、推奨を1つ)、補った点(番号付き。見方・根拠・覆したときの影響)、
       ユーザーに聞くこと(選択肢の形)
  → メインが、AskUserQuestion で、ユーザーに、解釈案を示し、合意を取る
  → 補った点を、依頼票(軽作業は納品書の依頼欄)の「こう理解した」の下に、番号付きで記録する。
       状態は、合意・変更・却下のいずれか。却下した点も残す
  → 完了の判定に、補った点ごとの項目を足す(「体感として合っているか。ユーザーが触って確認」)
  → 以降は、通常の流れ(spec・plan・implement、検査、納品書)
  → 検収で、ユーザーが、補った点を1点ずつ、承認または覆す
       覆すとき: 依頼票の追記(取り消し・変更)として受け、作業に戻る
```

### 5-2. 6つの見方(ユーザーが承認。通読の結果で、5つから見直した)
1. **遊びの核**: 何が面白さの中心か。核を決めて、それ以外は削る。優先順位をつける。
2. **遊ぶ人を第一に**: 誰が、どんな場面で遊ぶか。
3. **触って磨く**: 操作の手触りを、作って試して直す。
4. **迷わなさ**: 初見でも、何をすればよいか伝わるか。
5. **壊れ方・品質・想定外への備え**: 壊れ方、ありえない使われ方、品質・安全・不正への備え。QA にあたる見方。(当初は「想定外の遊ばれ方」。通読で、ゲームの遊ばれ方としての根拠は乏しく、品質・安全・負荷・不正への備えとしての根拠が多いと分かったため、広げた。根拠の大半は、ゲーム開発ではなく、周辺職種の記事)
6. **世界観・らしさの一貫**: 音、見た目、演出で、作品の印象をそろえる。(通読で見つかった、5つに入らない有力な候補。ゲーム制作に直結する記事が 10 本)

根拠の記事の番号と、通読の方法・限界は、`docs/ゲーム制作/観点の検証メモ.md`。

### 5-3. 呼ぶ条件
- 依頼が、ゲームの体験・仕様・操作に関わり、解釈が要るとき(私の判断)。原因が明らかな不具合の修正や、ドキュメントだけの変更では、呼ばない。
- ユーザーが「相談して」「どう思う?」と頼んだときは、いつでも呼ぶ。
- 呼ぶ指示は、`.claude/rules/window.md` の本件と軽作業の経路に書く。
- 軽作業でも、実装の変更がゲームの体験(遊び心地、操作、見え方)に関わるときは、呼ぶ。軽作業には依頼票がないため、補った点は、納品書の「依頼」欄の、「こう理解した」の下に、番号付きで書く。覆すときは、納品書を承認せず、補った点の取り消しを、依頼として受け、作業に戻る。

### 5-4. 相談役の定義
- ファイル: `.claude/agents/game-advisor.md`(英語。既存のエージェントと同じ)。
- `tools: Read, Grep, Glob`。`Edit`、`Write`、`Bash`、`Agent` は持たせない。
- `model: opus`(私の判断。判断の質を優先する。呼ぶ回数が少ないため)。
- 指示の要点:
  - 最初に、`docs/ゲーム制作/README.md` と、6つの見方のファイルを `Read` する(サブエージェントには、rules が自動で届かないため)。
  - 依頼を、勝手に決めて進めない。解釈案と、補った点を返す。
  - 補った点は、必ず、どの見方か、どの出典に基づくかを書く。出典のない一般論は、「出典なし(一般論)」と明記する。
  - ユーザーに聞くことは、選択肢の形で返す。
  - 報告は日本語。

### 5-5. 知識(種)
- 置き場所: `docs/ゲーム制作/`。
  - `README.md`: 目的、6つの見方の一覧、使い方。
  - `観点/1-遊びの核.md` から `6-世界観とらしさの一貫.md`: 見方の説明、相談役が投げる問い、根拠(出典付きの要約)、失敗の兆候。
  - `出典.md`: 記事の番号、題名、URL、職種、取得日、どの見方に使ったか。
- 種: 見方に合う十数本の記事を、本文まで読んで要約する。見方 5 は、ゲーム開発の記事から探し直す。
- 要約のみ。引用は、短く(1つの記事から、1か所、15 語未満)。出典の URL を必ず付ける。

### 5-6. 依頼票と納品書の変更
- spec の依頼票(`.specify/templates/overrides/spec-template.md`)に、「相談役が補った点」の節を足す。番号付き(例: A-1、A-2)。各行に、見方、内容、覆したときの影響。
- 納品書のテンプレート(`docs/納品書/_template.md`)に、補った点ごとの報告の書き方を足す。
- 概念図(`docs/実装フロー/概念図.html`)の戻る条件に、「補った点を覆す」を足す(手順 7 で、1点を覆すと、依頼票の追記として、手順 4 に戻る)。

### 5-7. 作るもの
| 成果物 | 内容 |
|---|---|
| `.claude/agents/game-advisor.md` | 相談役(英語) |
| `docs/ゲーム制作/` | 知識の種(README、6つの見方、出典) |
| `.claude/rules/window.md` と `docs/rules-ja/window.md` | 相談役を呼ぶ条件、委任メッセージの形式、合意の取り方、補った点の記録、覆し方 |
| `.specify/templates/overrides/spec-template.md` | 「相談役が補った点」の節 |
| `docs/納品書/_template.md` | 補った点ごとの報告 |
| `.claude/agents/window-verifier.md` | 補った点を受け取る。体感の項目の扱い(5-9) |
| `AGENTS.md`、`docs/実装フロー/` の 2 つの HTML | 相談役の説明を追記 |

### 5-8. 検証の方針
新しいセッションで、次を試す。
1. 抽象的な依頼(例: 「遊びやすい、短時間で遊べるパズルゲームを作りたい」)で、相談役が呼ばれ、解釈案と、番号付きの補った点が返る。
2. 補った点のそれぞれに、見方と出典が書かれている。出典のない一般論は、そう明記されている。
3. 合意の前に、仕様や実装に進まない。
4. 合意した補った点が、依頼票に記録され、納品書に、補った点ごとの項目がある。
5. 検収で、補った点を1点、覆すと、依頼票の追記として、作業に戻る。
6. 相談役が、ファイルを書き換えない。記事の本文が、そのまま、知識のファイルに入っていない。
7. 原因が明らかな不具合の修正では、呼ばれない。

質の確認: 抽象的な依頼を3件用意し、相談役の返答が、6つの見方のうち、どれに触れ、どの出典を使ったかを、ユーザーが読んで評価する。

### 5-9. 補った点の扱い(読み手役の確認で出た質問への、私の判断)

| 項目 | 扱い |
|---|---|
| 状態 | 合意・変更・却下。却下した点も、依頼票(軽作業は納品書の依頼欄)に残し、再提案を防ぐ |
| 全案が却下されたとき | 却下の理由を添えて、相談役を再び呼ぶ。ユーザーが方向を指定したときは、それを原文として渡す |
| 完了の判定との対応 | 補った点ごとに、完了の判定の項目を足す。納品書の節は、判定の項目と1対1のまま(補った点ごとの節ができる) |
| 体感の項目 | 「体感として合っているか」は、確かめる者が検査できない。確かめる者には、補った点を渡し、体感の項目は、「ユーザー検収」と書いて、判定の対象外にする。納品書の「確認していないこと」に、「ユーザーが触って確認する」と、常に書く |
| 見方の名前 | 番号(1〜5)と名前を固定して、依頼票・納品書に書く。見方が変わるときは、番号を振り直さず、廃止した番号は欠番にし、新しい番号を足す |
| 委任メッセージ | ユーザーの原文は、要約せず、そのまま貼る。聞き取りで分かったことは、別の節に、「メインの理解」として書く(原文と区別する)。結論やヒントは書かない |
| 種の本数 | 見方ごとに、最低 2 本。見方 5 は、ゲーム開発の記事が少ないため、ハードウェア開発やネットワークサービス開発の記事を使い、職種を明記する。ゲーム開発の記事が見つかれば、差し替える |
| spec-kit | この設計書を `/speckit-specify` の入力にして、`specs/003-game-advisor/` に spec を作る。計画の正本は、`specs/003-game-advisor/plan.md` |

## 6. ユーザーの決定
- 目的: 仕様を詰めるときと、実装を変えるときの、助言役・QA 的な、質の高い第三者。ゲーム制作の考え方を、ハーネスに持たせる。
- 呼ぶ時点: brainstorming の中。
- 自律の度合い: 提案して合意を取る。検収で、補った点を覆せる。決めて進むことはしない(4-2)。
- 見方: 当初の5つを、通読の結果で、6つに見直した(5-2)。見方 5 を「壊れ方・品質・想定外への備え」に広げ、見方 6「世界観・らしさの一貫」を足した。
- 作り方: 案 A(別の文脈のエージェント)。
- 順序: 仕組みが先。見方に合う十数本の記事で、小さく始める。

## 7. このドキュメントでの私の判断(ユーザーが決めていないもの)
- 呼ぶ条件(5-3)と、呼ばない場合。
- `model: opus`、`tools: Read, Grep, Glob`。
- 補った点の番号の付け方(A-1、A-2)。
- 知識の置き場所とファイルの構成(5-5)。要約と引用の上限。
- 合意の取り方: メインが、`AskUserQuestion` で、解釈案を示す。
- 覆すときは、依頼票の追記として扱い、作業に戻る。相談役は、置き換えに新しい解釈が要るときだけ、再び呼ぶ。
- 質の確認の方法(5-8)。
- 軽作業でも呼ぶこと、軽作業の記録先、覆し方(5-3)。
- 補った点の扱い全般(5-9): 状態、却下の保存、全案却下のとき、完了の判定との対応、体感の項目、見方の番号、委任メッセージ、種の本数、spec-kit への載せ方。

## 9. 未決(builder への申し送り)
1. 種に使う記事の選定(見方ごとに最低 2 本。見方 5 は、ゲーム開発の記事から探し、なければ、職種を明記して他の職種の記事を使う)。
2. 解釈案と補った点の、出力の細かい形式。
3. 「解釈が要るとき」の線引きの、実際の運用(呼びすぎ・呼ばなすぎ)。
4. 質の評価の基準(「質の高い」を、どう確認するか)。
5. `window-verifier` の指示の、体感の項目の扱いの、具体的な書き方。
