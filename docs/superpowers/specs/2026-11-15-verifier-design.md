# 確かめる者の設計

お客様モデル(`docs/ハーネス設計/お客様モデル_役所の手続きとトヨタの自工程完結.md`)の「確かめる者」を、このハーネスに実装するための設計。窓口(`docs/superpowers/specs/2026-11-15-window-design.md`)の次の段階にあたる。

- 状態: 草案(ユーザーの承認前)
- 作成日: 2026-11-15

## 1. 意図と、その理由

### 意図
作られたものを、作った者とは別の文脈で検査する役を置く。検査するのは、(1) 納品書の主張が、完了の判定を満たしているか、(2) 納品書の「確認していないこと」に抜けがないか、(3) 変更したコードの質(言語・エンジン別のレビュー)。

### 理由
- 窓口の第1版では、作った者(メインの会話)が納品書も書く。「確認していないこと」は自己申告で、抜けがあっても、誰も指摘しない。
- お客様モデル 3-6 は、「作った者は、答えになっているかを判定できない」と述べる。
- 現状のレビュー用エージェント(`.claude/agents/` の C++・C#・Rust 用)は、どの手順にも組み込まれておらず、呼ばれるかは Claude の自動判断任せである。Unity と Unreal 用はない。
- テストは、言語・エンジンごとの `testing.md` に、書き方の指針があるだけで、完了前に通す関門になっていない。

## 2. 目標・非目標・アンチゴール

### 目標
1. 本件の完了前に、必ず独立した検査を通す。
2. 軽作業は、コードやテストを変えたときだけ、独立した検査を通す。
3. 検査の報告の全文を、納品書に、改変せずに追記する。第1版は、メインによる改変を検知しない(5-6)。
4. 言語・エンジン別のレビュー(C++・C#・Rust・Unity・Unreal)を、検査の一部として確実に呼ぶ。

### 非目標
- 引き継ぎ票。当面使わない。
- 検査役がコードを修正すること。
- 検査の強制の仕組み(sandbox、フックによる書き込みの遮断)。第1版では、指示と制限に留める(5-6 の限界を参照)。
- 窓口の判定や、納品書の承認(ユーザーが行う)を、検査役が代わりに行うこと。

### アンチゴール(動いても失敗とみなすもの)
- 検査役が、ほぼ毎回「指摘あり」を出し、スタイルの指摘で報告が埋まる。
- 検査役の報告が、メインを経由して、取捨選択される。
- 納品書の確認方法を、すべて独立に再実行し、費用が検査の価値を超える。
- 検査役が、窓口の「2つ目の窓口」になる。作られたものの正しさを見て、依頼の照合はしない。

## 3. 制約(確認できた事実)

出典: https://code.claude.com/docs/en/sub-agents.md、https://code.claude.com/docs/en/best-practices.md、https://code.claude.com/docs/en/permissions.md、https://www.anthropic.com/engineering/harness-design-long-running-apps

- サブエージェントは、既定で、さらにサブエージェントを呼べる(3階層まで)。定義の `tools` に `Agent` を含める。サブエージェント定義内の `Agent(type)` の絞り込みは無視される。
- サブエージェントは、会話の履歴を見られない。見えるのは、委任メッセージと、`AGENTS.md` を含む指示ファイルだけ。ユーザーの原文と納品書は、メインが委任メッセージに貼る必要がある。
- 戻り値は要約だけ。長さの上限は、未検証。
- 読み取り専用の強制は、確実でない。親が `auto` や `acceptEdits` の権限モードだと、サブエージェントの `permissionMode` は無視される。Bash の許可規則は、コマンド文の照合で、セキュリティの境界ではない。
- Agent ツールの `subagent_type` で、名前を指定して呼べる(このセッションで確認)。
- Anthropic の見解: 検証の基本は、実装者が、pass/fail で判定できる確認を回し、証拠(コマンドと出力)を出すこと。自己採点は甘くなりやすく、採点が曖昧なタスクでは、独立した評価役が効く。ただし、分離だけでは甘さは消えず、懐疑的に調整する必要がある。別の文脈は、トークンと時間が増える。
- 既存のレビュー用エージェント(`cpp-reviewer`、`csharp-reviewer`、`rust-reviewer`)は、`tools: Read, Grep, Glob, Bash`、`model: sonnet`。変更を、自分で `git diff` で取る。
- rules は英語で書き、日本語訳を `docs/rules-ja/` に置く(AGENTS.md の方針)。`vendor/` は編集しない。

## 4. 検討した案

### 4-1. 何を、どこまで検査するか(ユーザーが案 1 を選択)
| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **1(採用)** | 作る者が、納品書に証拠(コマンドと出力)を貼る。確かめる者は、判断が要る部分(完了の判定との照合、確認していないことの抜け)と、言語別のレビューを検査し、再実行は抜き取りにする | 独立性が要る部分に費用を絞れる | 抜き取りの外の主張は、証拠を信じる |
| 2 | 納品書の確認方法を、すべて独立に再実行し、レビューも行う | 最も確実 | トークンと時間が最も増える。公式も、単独でこなせる範囲では評価役は余計な負荷になりうると述べる |
| 3 | 自己検証を強化し、独立したレビューは本件だけにする | 最も軽い | ユーザーが選んだ「軽作業のコード変更時も検査する」と、ずれる |

### 4-2. 言語別のレビューを、誰が呼ぶか(ユーザーが案 A を選択)
| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A(採用)** | 確かめる者が、入れ子で、言語別のレビューを呼び、1つの報告にまとめる | メインが指摘を取捨選択できない。独立性が高い | 入れ子が実際に動くかは、実機で確かめる必要がある |
| B | メインが、確かめる者と言語別のレビューを、別々に並行して呼ぶ | 仕組みが簡単 | 報告をまとめるのが作った者になる |

## 5. 設計

### 5-1. 流れ
```
作る者(メイン)が作業する
  → 納品書を書く(「確認した方法」に、コマンドと出力を貼る)
  → 検査が必要か判定する
       本件: 必ず。軽作業: 作業の差分にコードまたはテストが含まれるときだけ
  → 確かめる者を呼ぶ(subagent_type: window-verifier)。委任メッセージに、
       ユーザーの原文、依頼票、納品書の本文、変更ファイルの一覧を貼る。
       軽作業には依頼票がないため、納品書の「依頼」欄に全文で書いた「こう理解した」と「やらないこと」を、依頼票の代わりにする
  → 確かめる者が、検査し、言語別のレビューを入れ子で呼び、1つの報告を返す
  → メインが、報告を、納品書の末尾の「確かめる者の報告」の節に、そのまま追記する
  → 判定が「要修正」なら、作る者が直し、納品書を更新し、確かめる者を呼び直す(最大2回)。
       3回目にも「要修正」が出たら、作業を止めず、未解決の指摘を報告の節に載せたまま「確認待ち」で報告する。
       「判定不能」は、直せないため、差し戻しに数えず、そのまま報告する
  → 納品書を「確認待ち」で報告する(承認はユーザーが行う)
```

### 5-2. 検査が必要かの判定
- 本件は、必ず通す。
- 軽作業は、作業の差分(`git diff` と、未追跡のファイル)に、次のいずれかが含まれるとき通す。
  - ソースファイル: `.cpp` `.hpp` `.cc` `.hh` `.cxx` `.h` `.cs` `.rs`
  - テストファイル: `tests/` または `Tests/` 配下、ファイル名に `Test` または `_test` を含むもの
- ドキュメント、rules、設定、HTML だけの変更は、対象外。
- 迷ったら、検査する側に倒す(窓口の「迷ったら重い層」と同じ向き)。

### 5-3. 確かめる者の定義
- ファイル: `.claude/agents/window-verifier.md`(英語)。
- `tools: Read, Grep, Glob, Bash, Agent`。`Edit` と `Write` は含めない。
- `model: sonnet`。
- 指示の要点:
  - 作られたものを、懐疑的に検査する。納品書の主張を、そのまま信じない。
  - ファイルを書き換えない。Bash は、読み取りと検査の実行にだけ使う。
  - スタイルだけの指摘は、報告に含めない(指摘は必ず何か出る、という偏りを避ける)。
  - 報告の言語は日本語。
- 検査の内容:
  1. 納品書の「完了の判定ごとの報告」を、完了の判定の各項目に照合し、満たす・満たさない・判定不能を、根拠(`path:line` またはコマンド出力)つきで書く。
  2. 「確認していないこと」の抜けを指摘する。対象は、完了の判定の項目に直結する抜け、つまり、その項目の主張を、確認方法が捕まえていない場合だけ。一般的な懸念は、「補足」として書き、指摘に数えない。
  3. 納品書の確認方法のうち、実行できるコマンドを、最大3つ再実行する(私の判断。最も重要なものを選ぶ)。
  4. 変更ファイルの拡張子とパスに応じて、言語別のレビューを入れ子で呼ぶ(5-4)。CRITICAL と HIGH の指摘は、そのまま報告に含める。

### 5-4. 言語別のレビュー
| 変更 | 呼ぶエージェント |
|---|---|
| `.cpp` `.hpp` `.cc` `.hh` `.cxx` `.h`(Unreal を除く) | `cpp-reviewer`(既存) |
| `.cs`(Unity を除く) | `csharp-reviewer`(既存) |
| `.rs` | `rust-reviewer`(既存) |
| `Assets/**` の `.cs` | `unity-reviewer`(新規) |
| `Source/**`、`Plugins/**/Source/**` の `.h` `.cpp` `.cs` | `unreal-reviewer`(新規) |

重なりと対象外の扱い:

- 重なるファイルは、特化側だけを呼ぶ(AGENTS.md の「Unity は `unity/`、Unreal は `unreal-engine/` を優先」と同じ)。`Assets/` と `Source/` が1つの変更に混在するときは、両方を呼ぶ。
- 上の表にない拡張子(`.py`、`.js`、シェルスクリプト、`.shader`、`.uasset` など)は、検査は通しても、言語別のレビューは呼ばず、報告に「対象外」と書く。

新規の `unity-reviewer` と `unreal-reviewer` は、`.claude/agents/` に置く(英語)。既存と同じ `tools: Read, Grep, Glob, Bash`、`model: sonnet`。指示は、それぞれの rules(`.claude/rules/unity/`、`.claude/rules/unreal-engine/`)を読み、その規約とパターンに照らして、変更を検査する。

### 5-5. 検査の報告の形式
確かめる者は、次の形式で、日本語で返す。

```
## 確かめる者の報告

判定: 承認可 / 要修正 / 判定不能

### 完了の判定との照合
- <項目>: 満たす / 満たさない / 判定不能 — 根拠: <path:line またはコマンド出力>

### 確認していないことの抜け
- <抜け。なければ「なし」>

### 再実行の結果
- <コマンド>: <結果>

### レビューの指摘
- <レビューしたエージェント>: <CRITICAL / HIGH の指摘を、そのまま。なければ「なし」>

### 確かめる者が確認していないこと
- <この検査では捕まえられないもの。空欄不可。なければ「なし」>
```

### 5-6. 書き込みの防止と、その限界
- `Edit` と `Write` を `tools` に含めず、指示で書き換えを禁じる。
- 限界(確認した事実): Bash からは、ファイルを書き換えられる。親が `auto` などの権限モードのとき、サブエージェントの `permissionMode` は無視される。Bash の許可規則は、セキュリティの境界ではない。
- メインが、確かめる者の報告を、改変して追記しても、第1版では検知しない。報告の全文を、そのまま納品書に追記することを、`window.md` の規則とする。
- 第1版では、これ以上の強制(PreToolUse フック、sandbox)は作らない。検査役が書き換えをしていないかは、第1版では検査しない。報告の「確かめる者が確認していないこと」に、その旨(書き換えの有無を確認していない)を書かせる。

### 5-7. 納品書の変更
- 「確認した方法」に、コマンドと出力(要点)を貼ることを必須にする(Anthropic の「証拠を求める」に従う)。
- 末尾に、「確かめる者の報告」の節を足す。検査が不要だった場合は、その旨と理由(「ドキュメントだけの変更」など)を、1行で書く。
- テンプレート `docs/納品書/_template.md` と、窓口の経路(`.claude/rules/window.md` と訳)を更新する。

### 5-8. 作るもの
| 成果物 | 内容 |
|---|---|
| `.claude/agents/window-verifier.md` | 確かめる者(英語) |
| `.claude/agents/unity-reviewer.md`、`.claude/agents/unreal-reviewer.md` | Unity と Unreal のレビュー(英語) |
| `.claude/rules/window.md` と `docs/rules-ja/window.md` | 検査が必要かの判定、確かめる者の呼び方、報告の追記、差し戻し(最大2回) |
| `docs/納品書/_template.md` | 証拠の必須化、「確かめる者の報告」の節 |
| `AGENTS.md`、`docs/実装フロー/実装フロー.html` | 確かめる者の説明を追記 |

### 5-9. 検証の方針
- 新しいセッションで、次を試す。
  1. 本件で、確かめる者が呼ばれ、報告が納品書に追記される。
  2. コードを変えた軽作業で、呼ばれる。ドキュメントだけの軽作業で、呼ばれない。
  3. 入れ子で、言語別のレビューが呼ばれ、CRITICAL と HIGH の指摘が報告に含まれる。
  4. わざと不備のある納品書(確認していないことの抜け)を渡し、検査役が指摘する。
- 入れ子が動かない場合は、案 B に切り替える。

## 6. ユーザーの決定
- 範囲: 案 1(証拠を必須にし、独立した検査は判断が要る部分に絞る)。
- 検査の対象: 本件は必ず。軽作業は、コードやテストを変えたときだけ。
- 検査の中身: 納品書の検証と、言語別のレビュー(Unity と Unreal の汎用のレビューを新しく作る)。
- 言語別のレビューの呼び方: 案 A(確かめる者が入れ子で呼ぶ)。

## 7. このドキュメントでの私の判断(ユーザーが決めていないもの)
- 検査が必要かの判定(5-2)の、拡張子とテストファイルの線引き。
- 確かめる者を呼ぶときの `subagent_type` の名前: `window-verifier`。
- `model: sonnet`。
- 再実行の上限: 3つ。
- 差し戻しの上限: 最大2回。
- 検査の報告の形式(5-5)。
- 検査の報告を、納品書の末尾に、そのまま追記する(第1版は、改変を検知しない)。
- 軽作業の完了の判定の正本: 納品書の「依頼」欄に全文で書いた「こう理解した」と「やらないこと」。
- 差し戻し上限を超えたときと、「判定不能」の扱い(5-1)。
- Unity と Unreal の重なりと、レビュー先がない拡張子の扱い(5-4)。
- 「確認していないこと」の抜けの基準(5-3)。
- spec は `specs/002-request-verifier/` とし、新しいセッションが要る実機検証(5-9)は、ユーザーの手が要るタスクとして含める。
