# 依頼の窓口

ユーザーのどの発言も、最初に窓口を通る。作業を求めない発言(質問)は、`window-question` スキルが答え、層は判定しない。作業を求める発言は、軽作業か本件かを判定し、その依頼にどれだけの手続きが要るかを決める。フックが、毎ターン、これを思い出させる。

## 層

| 層 | 条件 |
|---|---|
| 軽作業 | 取り返しがつき、小さく、spec に残すほどではない(不具合修正、小さな変更)。 |
| 本件 | 取り返しがつかない、外向きである、または判断が設計に及ぶ。新規実装を含む。 |

## 層の判定

2つの軸で判定する。

- 取り返しがつくか。外向きの操作(公開、送信、push、マージ)を含むか。
- 判断に分岐があり、複数の選択肢が成り立つか。

規則:

- 判定するのは、ユーザーの作業の依頼だけ。質問には層がない。システムの通知(バックグラウンドタスクの結果など)は無視する。
- 迷ったら、重い層を選ぶ。
- 層は下げない。軽作業が、取り返しのつかない操作を要すると分かったら、本件に上げて、ユーザーに伝える。
- 質問と作業の依頼が混ざった発言は、作業の層で扱う。

## 検査

納品書を書いた後、検査が必要なとき(下の経路を参照)は、納品書を報告する前に、`window-verifier` エージェントを呼ぶ。

1. `Agent` ツールで、`subagent_type: window-verifier` を指定して呼ぶ。
2. 委任メッセージには、次を、別々の節として貼る: ユーザーの原文(要約しない)、依頼票(本件)、または納品書の依頼欄の「こう理解した」と「やらないこと」の全文(軽作業。相談役を呼んだときは、補った点の表を含む)、納品書の全文、変更ファイルの一覧(`git diff --name-only` と `git ls-files --others --exclude-standard`)、依頼の層、検査の回数。確かめる者は、この会話を見られない。
3. メッセージに、自分の判断やヒント(「問題ない」「ここを見て」など)を書かない。
4. 確かめる者の報告は、納品書の末尾の「確かめる者の報告」の節に、全文を、書き換えずに追記する。
5. 判定が承認可なら、納品書を「確認待ち」と報告する。承認はユーザーが行う。
6. 判定が「要修正」なら、作業を直し、納品書を更新して、確かめる者を呼び直す(最大2回)。新しいメッセージに、前回の判定を書かない。3回目にも要修正なら、作業を止めず、未解決の指摘を報告の節に載せたまま、納品書を「確認待ち」と報告する。
7. 判定が「判定不能」なら、回数に数えず、そのまま報告する。

## 相談役

作業の依頼(軽作業・本件)の内容を詰めている間に、次のどれかに当たるときは、`game-advisor` エージェントを呼ぶ。

- ゲームの体験(遊び心地、操作、見え方、遊びの流れ)を、新しく決める、または変える。
- 依頼の言葉が抽象的で、複数の解釈があり、解釈によって、遊ぶ人の体験が変わる。
- ユーザーが助言を求めた(「相談して」「どう思う?」など)。このときは、必ず呼ぶ。

原因が明らかな不具合の修正、ドキュメントだけの変更、体験に関わらない内部の整理では、呼ばない。迷ったら、呼ぶ。

1. `Agent` ツールで、`subagent_type: game-advisor` を指定して呼ぶ。相談役は、この会話を見られない。委任メッセージは4つの節: (1) ユーザーの原文(要約せず、そのまま)、(2) メインの理解と層(ユーザーの言葉とは別に書く。結論やヒントは書かない)、(3) 再び呼ぶときだけ、却下・変更された補った点と、ユーザーの理由、ユーザーが指定した方向(原文のまま)。初回は「なし」、(4) 求めること: 解釈案と補った点を返す。
2. 相談役の解釈案と質問を、`AskUserQuestion` で、ユーザーに示す。ユーザーが合意する前に、spec・計画・実装に進まない。相談役は、決めない。
3. 補った点は、番号(A-1、A-2…)、見方、内容、覆したときの影響、状態(合意・変更・却下)つきで記録する。却下した点も残す。本件は、依頼票の「こう理解した」の下。軽作業は、納品書の依頼欄の「こう理解した」の下。
4. 合意(または変更)した補った点ごとに、完了の判定の項目を 1 つ足す。体感の項目は、行頭に `[ユーザー検収]` を付ける。確かめる者は、その項目を判定しない。納品書の「確認していないこと」には、「ユーザーが触って確認する」と、常に書く。
5. すべての解釈案が却下されたときは、理由を添えて(メッセージの節 3)、相談役を再び呼ぶ。
6. 検収で、ユーザーは、補った点を 1 点ずつ覆せる。依頼の追記として受け、その点の状態を、却下または変更に直して、作業に戻る。置き換えに新しい解釈が要るときだけ、相談役を再び呼ぶ。

## 経路

### 質問(層なし)

`window-question` スキルを、名前で呼ぶ。層は判定せず、依頼票、納品書、層の宣言は出さない。答えから書き、根拠(`path:line`、URL、コマンドの出力)は、ユーザーが行動するのに役立つ場合にだけ示す。答えるのに、ファイルや状態の変更が要ると分かったら、作業の依頼として扱い、その時点で層を判定する。

### 軽作業

- brainstorming は、作業の大きさを測り、足りない点を聞くためだけに使う。設計メモは書かず、`writing-plans` にも進まない。
- 変更がゲームの体験に関わるときは、作業の前に「相談役」の節に従う。補った点は、納品書の依頼欄の「こう理解した」の下に書く。
- 作業は、メインの会話で行う。不具合には `systematic-debugging`、テストが当てはまる場面では `test-driven-development`、何かを完了と言う前には `verification-before-completion` を使う。
- 終わったら、`docs/納品書/_template.md` から、`docs/納品書/<YYYY-MM-DD>-<題名>.md` に納品書を書く。ユーザーと確認した項目(こう理解したこと、やらないこと)ごとに1つの節を置き、各節に3つの欄を埋める: 何をしたか、確認した方法(手順を書く。「確認した」だけは不可)、確認していないこと。最後の欄は空にしない。当てはまるものがなければ「なし」と書く。
- 納品書の依頼欄に、こう理解したことと、やらないことを、全文で書く。
- 検査を通すのは、差分(`git diff --name-only` と `git ls-files --others --exclude-standard`)に、ソースファイル(`.cpp` `.hpp` `.cc` `.hh` `.cxx` `.h` `.cs` `.rs`)またはテストファイル(`tests/` か `Tests/` 配下、ファイル名に `Test` か `_test` を含むもの)があるときだけ。その場合は、「検査」の節に従う。ドキュメント、rules、設定、HTML だけの変更は、確かめる者を呼ばず、納品書の最後の節に、検査が不要だったことと理由を、テンプレートの形で1行書く。迷ったら、検査する。
- 検査の後(検査が必要なとき)、納品書を「確認待ち」と報告する。完了とは言わない。納品書の承認は、ユーザーが行う。
- ユーザーが頼んでいない作業を足したときは、納品書の「追加した項目」に書く。

### 層を上げる

- 外向きの操作(push、プルリクエストの作成、マージ)を含む依頼は、本件として扱い、先にユーザーに確認する。
- ローカルの commit、ドキュメントだけの変更、rules や設定ファイルの編集は、軽作業。
- 軽作業が、取り返しのつかない操作を要すると分かったら、本件に上げて、ユーザーに伝える。層は下げない。

### 本件(新規実装)

- brainstorming から始め、続けて `/speckit-specify` に進む。spec の先頭は、5つの欄を持つ依頼票とする: ユーザーの言葉をそのまま引用したもの(要約しない)、こう理解したこと、誰のためか、やらないこと、完了の判定。
- 依頼が「相談役」の節に当たるときは、依頼を最初に読んだ後、依頼票の残りの欄を埋める前に、その節に従う。補った点は、依頼票に記録する。
- まだ空の欄についてだけ、`AskUserQuestion` で、選択肢の形で聞く。自由記述で聞いてよいのは、ユーザーだけが持つ事実に限る。
- ユーザーが「やらないこと」と「完了の判定」に合意するまで、計画にも実装にも進まない。
- 実装が終わったら、`docs/納品書/_template.md` から、`docs/納品書/<NNN-feature>.md`(`specs/<NNN-feature>/` と同じ名前)に納品書を書く。完了の判定の各項目に1つの節を置く。軽作業と同じ規則に従う: 1節に3つの欄、最後の欄は空にしない。「確認した方法」の欄には、コマンドと出力(要点)を貼る。
- 納品書を報告する前に、必ず「検査」の節に従う。その後、「確認待ち」と報告し、完了とは言わない。
