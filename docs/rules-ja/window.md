# 依頼の窓口

ユーザーのどの発言も、最初に窓口を通る。窓口は、その依頼にどれだけの手続きが要るかを判定し、経路に回し、結果を報告する。フックが、毎ターン、これを思い出させる。

## 層

| 層 | 条件 |
|---|---|
| 質問 | 作業がない。ファイルや状態が何も変わらない。 |
| 軽作業 | 取り返しがつき、小さく、spec に残すほどではない(不具合修正、小さな変更)。 |
| 本件 | 取り返しがつかない、外向きである、または判断が設計に及ぶ。新規実装を含む。 |

## 層の判定

2つの軸で判定する。

- 取り返しがつくか。外向きの操作(公開、送信、push、マージ)を含むか。
- 判断に分岐があり、複数の選択肢が成り立つか。

規則:

- 判定するのは、ユーザーの発言だけ。システムの通知(バックグラウンドタスクの結果など)は無視する。
- 迷ったら、重い層を選ぶ。
- 層は下げない。軽作業が、取り返しのつかない操作を要すると分かったら、本件に上げて、ユーザーに伝える。
- 質問と作業の依頼が混ざった発言は、作業の層で扱う。

## 経路

### 質問

`window-question` スキルを、名前で呼ぶ。依頼票、納品書、層の宣言は出さない。答えから書き、根拠(`path:line`、URL、コマンドの出力)は、ユーザーが行動するのに役立つ場合にだけ示す。答えるのに、ファイルや状態の変更が要ると分かったら、層を上げて、ユーザーに伝える。

### 軽作業

- brainstorming は、作業の大きさを測り、足りない点を聞くためだけに使う。設計メモは書かず、`writing-plans` にも進まない。
- 作業は、メインの会話で行う。不具合には `systematic-debugging`、テストが当てはまる場面では `test-driven-development`、何かを完了と言う前には `verification-before-completion` を使う。
- 終わったら、`docs/納品書/_template.md` から、`docs/納品書/<YYYY-MM-DD>-<題名>.md` に納品書を書く。ユーザーと確認した項目(こう理解したこと、やらないこと)ごとに1つの節を置き、各節に3つの欄を埋める: 何をしたか、確認した方法(手順を書く。「確認した」だけは不可)、確認していないこと。最後の欄は空にしない。当てはまるものがなければ「なし」と書く。
- 納品書は「確認待ち」と報告する。完了とは言わない。納品書の承認は、ユーザーが行う。
- ユーザーが頼んでいない作業を足したときは、納品書の「追加した項目」に書く。

### 層を上げる

- 外向きの操作(push、プルリクエストの作成、マージ)を含む依頼は、本件として扱い、先にユーザーに確認する。
- ローカルの commit、ドキュメントだけの変更、rules や設定ファイルの編集は、軽作業。
- 軽作業が、取り返しのつかない操作を要すると分かったら、本件に上げて、ユーザーに伝える。層は下げない。

### 本件(新規実装)

- brainstorming から始め、続けて `/speckit-specify` に進む。spec の先頭は、5つの欄を持つ依頼票とする: ユーザーの言葉をそのまま引用したもの(要約しない)、こう理解したこと、誰のためか、やらないこと、完了の判定。
- まだ空の欄についてだけ、`AskUserQuestion` で、選択肢の形で聞く。自由記述で聞いてよいのは、ユーザーだけが持つ事実に限る。
- ユーザーが「やらないこと」と「完了の判定」に合意するまで、計画にも実装にも進まない。
- 実装が終わったら、`docs/納品書/_template.md` から、`docs/納品書/<NNN-feature>.md`(`specs/<NNN-feature>/` と同じ名前)に納品書を書く。完了の判定の各項目に1つの節を置く。軽作業と同じ規則に従う: 1節に3つの欄、最後の欄は空にしない、「確認待ち」と報告し、完了とは言わない。
