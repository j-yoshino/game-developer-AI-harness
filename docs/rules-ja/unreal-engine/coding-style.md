# Unreal Engine C++ コーディングスタイル

出典: https://dev.epicgames.com/documentation/unreal-engine/epic-cplusplus-coding-standard-for-unreal-engine?lang=ja(Unreal Engine 5.9 のドキュメント、日本語ページ、2026-11-15 に全文を読了)。Epic 社内の標準で、ページは遵守が必須だと述べています。

## 優先順位
- `Source/**/*.{h,cpp}` では、このファイルが `.claude/rules/cpp/coding-style.md`(ECC の記述と C++ Core Guidelines の節)より優先します。`Source/**/*.cs`(`*.Build.cs`、`*.Target.cs` などのビルドスクリプト)では、`.claude/rules/csharp/coding-style.md` より優先します(Epic は C# でもタブを使います)。`paths` ではファイルを除外できないため、どちらも読み込まれます。

| 項目 | C++ Core Guidelines / ECC | Unreal(こちらに従う) |
|---|---|---|
| 命名 | `underscore_style`(NL.10) | PascalCase と型ごとの接頭辞 |
| 波かっこ | K&R 由来(NL.17) | Allman(波かっこは新しい行) |
| `auto` | 使ってよい(ES.11)。ECC は構造化束縛も勧めている | `auto` を避ける。構造化束縛は使わない |
| 標準ライブラリ | 優先する(SL.1、SL.2) | 相互運用のコードを除き、標準のコンテナと文字列を避ける |
どちらも同じ: 列挙型は `enum class` を使う。

## 命名
- PascalCase。各単語の先頭を大文字にし、通常はアンダースコアを使わない。コードとコメントは米国英語のつづり。
- 型の接頭辞: `T` テンプレート、`U` UObject 派生、`A` AActor 派生、`S` SWidget 派生、`I` 抽象インターフェース、`C` コンセプト、`E` 列挙型、`F` その他の多くのクラスと構造体、`b` ブール値(必須)。C# では接頭辞を付けない。typedef は、別名を付ける対象の型の接頭辞を付ける。テンプレートパラメーターには `In` 接頭辞を使ってよい。
- マクロ: 大文字とアンダースコアで、`UE_` で始める。型と変数は名詞、メソッドは動詞、`bool` を返す関数は質問の形(`IsVisible()`)、プロシージャーは動詞と対象。曖昧な動詞(`Handle`、`Process`)を避ける。名前は明確で曖昧さがなく説明的にし、過度な省略を避ける。
- 参照渡しの出力引数には `Out` 接頭辞を付ける(`bool` は `bOutResult`)。変数は1行に1つ宣言し、直前にドキュメントコメントを書く。

## 移植性と標準ライブラリ
- サイズを明示した型を使う(`int32`、`uint8`、`int64`、`float`、`double`)。`int` のサイズに依存しない。`BOOL` ではなく `bool`。シリアル化とレプリケーションにはサイズを明示した型を使う。
- 標準ライブラリの利用は、歴史的に避けてきた。条件付きで使えるもの: `<atomic>`(新しいコード)、`<type_traits>`(小文字の `value` / `type`)、`<initializer_list>`(波かっこ初期化のためだけ)、`<regex>`(エディター専用コードにカプセル化)、`<limits>`、`<cmath>`。`memcpy` / `memset` は、性能上の利点が明確なときだけ。同じ API で UE のイディオムと標準のイディオムを混在させない。

## C++ の機能
- エンジンは C++20 でビルドされ、C++20 が必要。`static_assert`、`override`、`final`(強く推奨)、`nullptr`(`NULL` ではなく)を使う。
- `auto` は、変数に入れるラムダ、イテレーター、テンプレートコードを除いて使わない。構造化束縛も使わない。範囲ベース `for` を優先する(`TMap` は `Key` / `Value` を持つ `TPair` を返す)。
- ラムダ: 短く保つ。`[&]` / `[=]` ではなく明示的なキャプチャ。遅延実行では、参照キャプチャと `this` を避ける(`TWeakObjectPtr` を使う)。大きなラムダには戻り値の型を明示する。
- 従来の列挙型は `enum class` に置き換える(`UENUM` で使える。Blueprint に公開する列挙型は `uint8` でなければならない)。フラグ列挙型は `ENUM_CLASS_FLAGS` を使い、`None` を 0 にする。
- `const` は、引数・メソッド・ループ変数・ローカル変数に付けるが、戻り値の型には付けない(ムーブを妨げるため)。`MoveTemp` を使う。値渡しのシンク引数は、`const` の規則の例外。デフォルトのメンバー初期化子は使えるが、ヘッダーを変更すると再ビルドとパッチの制約が生じるため、ゲームコード向き。
- ページに書かれていないこと: 例外、RTTI、三項演算子、スレッドに関する規則。

## フォーマット
- Allman 形式の波かっこ。1つの文でも波かっこで囲む。`else if` は `if` と揃える。タブ、幅は4(C# でも)。スペースは揃えるためだけに使う。
- `switch`: 意図したフォールスルーにはコメントを付け、必ず `default` を置き、各ケースを `break` などで終える。ポインターと参照: 記号の後ろにスペース(`FShaderType* Ptr`)。関数名と `(` の間は空けない。ファイルの末尾に空行を1行。各ソースファイルの最初の行には、規定の著作権表示を正確に入れる。

## コメントと依存関係
- 自己説明的なコードを優先する。コメントは実装ではなく意図を書く。コードと一緒にコメントを更新する。マジックナンバーは名前付き定数に置き換える。
- JavaDoc 形式でドキュメントを書く: クラス(解決する問題と作った理由)、メソッド(公開の宣言に一度だけ。目的、各パラメーターの単位・範囲・不正な値、エラーの意味)。サードパーティのコードは、検索できる目印のコメントで囲む。
- `#pragma once`。使うものは、推移的な include に頼らず直接 include する。`Core.h` のような巨大なヘッダーを避ける。include より前方宣言。ヘッダー内で標準ライブラリのヘッダーを include しない。ファイル名に接頭辞を付けない(`Scene.cpp`)。モジュールごとに `Public` / `Private` フォルダー。`FORCEINLINE` は慎重に。ヘッダーに重い `static` 変数を置かない。

## API 設計と一般規則
- `bool` 引数を使わない(列挙型のフラグを使う)。引数が多いときは構造体にまとめる。`bool` と `FString` のオーバーロードを避ける。インターフェースは `I` で始め、メンバー変数を持たず、純粋仮想にする。`virtual` と `override` の両方を書く。UObject はポインターで渡す。メンバーは既定で private。派生させないクラスには `final`。新しい API は `UE::` 名前空間に置く(`UCLASS` / `USTRUCT` とマクロには使わない)。ヘッダーでグローバルな `using` をしない。実装の詳細は `Private` 名前空間に置く。
- プラットフォーム固有のコードは、プラットフォーム名のサブディレクトリーに置く。`PLATFORM_[PLATFORM]` のチェックを散らさず、`FPlatformMisc` のような抽象化レイヤーに static 関数を足す。
- 文字列リテラルは `TEXT()` で囲む。変数のシャドーイングをしない。複雑な式は分割する。デバッグコードをチェックインしない。挙動を変えない大規模な整形や名前変更は、別の変更にする。包摂的な用語を使う(allow / deny list、primary / replica)。
