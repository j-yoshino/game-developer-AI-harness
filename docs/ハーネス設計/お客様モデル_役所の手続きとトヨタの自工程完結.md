# お客様モデル — 役所の手続きとトヨタの自工程完結

AI エージェントに作業を頼むときの、責任と手続きのモデル。

> この文書はモデルそのものの定義であり、特定のハーネス・ツール・リポジトリに依存しない。
> 既存の仕組みへの当てはめは別途行う。

## 0. 参考にしたモデル

実社会の 2 つのモデルを組み合わせている。どちらも**そのまま写してはいない。**

| 出典 | 借りたもの | 変えたところ |
| --- | --- | --- |
| **役所の手続き** | **書式が決まった書類で境界を越える**こと。窓口という役、申請 → 受理、検収、所管外は受け付けない線引き、段取りの固定 | 役所は依頼の大小に関係なく同じ書類を要求する。ここでは**手続きの重さを判定して層を分ける**（4 節） |
| **トヨタの自工程完結 / 「後工程はお客様」** | 各工程が次工程を自分のお客様として扱い、不良を下流へ流さない。検査部門に頼らない | トヨタは物理的な製造工程の話。ここでは**書類の書式をそのまま内側の引き継ぎに再帰させる**（5-3） |

役所から「**書式で守る**」を、トヨタから「**自分の工程は自分で担保する**」を取っている。
役所の欠点（儀式が一律で重い）はトヨタ側の考え方で薄め、トヨタの前提（工程が物理的に分かれている）は
書式の再帰で埋めている。

## 1. 前提

登場するのは 2 者だけ。

| | お客様 | ベンダー |
| --- | --- | --- |
| 誰か | 作業を頼む人 | 作業するエージェント |
| 持っているもの | **何が欲しいか**（意図・目的・制約・好み） | **どう作るか**（手段・技術・手順） |
| 持っていないもの | 手段の知識、作業の時間 | 意図。お客様が言わない限り知る術がない |
| 立場 | 組織の**外**。要望を自分の言葉で言うだけ | 組織の**内**。聞き取りから納品まで負う |

**お客様は曖昧に言ってよい。** 要望が一度で正確に言語化されることはない。曖昧さを解消するのは
ベンダーの職務であり、お客様の不備ではない。

## 2. 責任の所在

モデルの核心はこの表である。以降の役職・書類・手続きはすべてここから導かれる。

| 事項 | 持ち主 |
| --- | --- |
| 何が欲しいか（意図） | **お客様** |
| 要望を正確に理解すること | **ベンダー**（分からなければ聞き返す義務がある） |
| 範囲の線引きの提案 | ベンダー |
| 範囲の承諾 | **お客様** |
| 作り方の選択 | ベンダー |
| 正しく作れたかの確認 | ベンダー |
| **確認の限界の開示** | **ベンダー** |
| 検収（受け取ってよいかの判断） | **お客様** |
| 好み・体感の判断 | **お客様** |
| 外向きの操作の承認（公開・送信・本番反映） | **お客様** |

読み方の要点は 2 つ。

- **「要望を正確に理解すること」はベンダー側にある。** お客様が言い間違えても、ベンダーが取り違えたまま
  作ったなら、それはベンダーの失敗である。
- **「確認の限界の開示」はベンダー側にある。** 何を確かめ、何を確かめていないかを言わないまま
  「できました」と言うのは、納品していないのと同じである。お客様は限界を知らずに検収できない。

## 3. 原則

### 3-1. 要約は枠を狭める

お客様の言葉を要約した時点で、要約した側の理解に枠が固定される。以降の作業はその枠の中でしか進まず、
**枠が狭かったことに誰も気づけない。** だから要望は原文のまま保持し、言い換えは原文と並べて提示する。

### 3-2. 検査の範囲が、主張できる範囲

「問題なし」は、使った検査方法の範囲でしか言えない。方法を言わない「問題なし」は、範囲不明の主張であり、
お客様はより広い確認を頼むことができない。**方法と結論は常に同じ場所に書く。**

### 3-3. 線引きは着手前に出す

やらないこと・できないことを作業後に出すと、お客様は範囲を交渉できない。判断の後に届く注意書きは
間に合っていない。**線引きは依頼の段階で提示し、承諾を得る。**

### 3-4. 完了の判定は依頼時に合意する

何をもって完了とするかを先に決めておけば、納品時はその一覧を照合するだけになる。考える負荷が
依頼時の 1 回に寄るため、工程ごとに承認を求めるより軽い。

### 3-5. 枠は散文ではなく書式で守る

「丁寧に伝えよ」「網羅的に調べよ」といった散文の規約は、書く側の裁量に依存するためブレる。
**埋めるべき欄があれば埋まり、空欄は欠落として見える。** 仕組みの本体は固定書式に置く。

### 3-6. 作った者は、答えになっているかを判定できない

作業したエージェントは自分が立てた枠に投資している。その枠の外は見えない。**依頼と回答の照合は、
作業していない者が行う。**

### 3-7. 後工程はお客様

各工程は、次の工程を自分のお客様として扱う。次工程へ渡す前に、自分の工程の完了条件を自分で確かめ、
**確かめた方法と確かめていないことを添えて渡す。**

確かめずに渡して検査役に拾わせるのは、不良を下流へ流すことである。**検査役は最後の網であって、
最初の網ではない。** 自分の工程の正しさは、自分の工程で担保する。

2 節は「正しく作れたかの確認はベンダー」とだけ定めている。この原則はそれを細分し、
**ベンダーの中の誰が確認するのかを「各工程が自分の分を」に確定させる。**

## 4. ベンダー側の役職

役職は「同じコンテキストでは構造的に無理なことがある境界」にだけ立てる。それ以外は書式で足りる。

| 役 | 職務 | 分かれる構造的な理由 |
| --- | --- | --- |
| **窓口** | **手続きの重さの判定**、聞き取り、線引きの提案、納品説明、依頼と回答の照合 | 作った者は自分の枠に投資しているので、答えになっているか判定できない（3-6） |
| **作る者** | 実際に手を動かす。**対象を書き換えるのはこの役だけ** | 複数が同じ対象を触ると衝突する |
| **確かめる者** | 作られたものの正しさを検査する | 同じコンテキストは自分の前提を疑えない |

この 3 つで足りる。役職を増やしたくなったときは上の「構造的な理由」の欄を書けるか試す。
書けないなら、それは役職ではなく書式で表現すべきものである。

**窓口は検査役ではない。** 作られたものの正しさは見ず、**回答が依頼に答えているかだけ**を見る。
この境界を守らないと、窓口は 2 つ目の検査役になり、本来の職務が薄まる。

### 手続きの重さの判定（窓口の最初の仕事）

聞き取りの前に、**その依頼にどれだけの手続きが必要か**を決める。依頼の大小に関係なく同じ書類を
要求すると、小さな依頼では手続きが依頼そのものより重くなる。

判定は主観ではなく 2 つの軸で行う。

| 軸 | 問い |
| --- | --- |
| **取り返しがつくか** | 元に戻せるか。外に出る操作（公開・送信・本番反映）を含むか |
| **判断の分岐があるか** | 選択肢が複数あり、どちらも成立するか |

| 層 | 条件 | 手続き |
| --- | --- | --- |
| **即答** | 取り返しがつく / 分岐なし | 書類なし。答えの中に、確かめた方法を書く |
| **軽作業** | 取り返しがつく / 分岐あり | 「こう理解した」と「やらないこと」の 2 つだけを示して確認を取る |
| **本件** | 取り返しがつかない、または分岐が設計に及ぶ | 依頼票と納品書を揃える（5 節） |

判定を誤ったと分かった時点で**層を上げる。下げてはいけない。** 作業中に取り返しのつかない操作が
必要だと判明したら、その時点で本件として扱い直す。

### 窓口に渡すもの

**お客様の原文と、作業の結果の両方。** 職務を照合に限定するため、この 2 つが揃っていなければ成立しない。

原文を渡さず作業側の要約だけを渡すと、窓口は**狭い要約を正確に取り次ぐだけ**になり、取り違えは
そのまま通る。原文があれば「お客様はこれを聞いているが、この回答は別のことを答えている」と言える。

## 5. 書類

境界を越えるのは 2 枚だけ。固定書式であることが仕組みの本体である（3-5）。
**どちらを使うかは 4 節の「手続きの重さの判定」で決まる。** 即答の層では書類を作らない。

### 5-1. 依頼票

窓口が書き、お客様が確認して確定する。

| 欄 | 書くこと | この欄が守る原則 |
| --- | --- | --- |
| ご要望 | **お客様の言葉をそのまま引用する。要約しない** | 3-1 |
| こう理解した | 言い換え。お客様はここだけ読めば誤解に気づける | 3-1 |
| 誰のためか | 誰が読む / 使う / 判断するのか | — |
| 伺いたい点 | 曖昧な点。**選択肢の形で聞く** | — |
| やらないこと | 線引き。範囲外・できないこと | 3-3 |
| 完了の判定 | 検収基準。お客様が納品時に照合する一覧 | 3-4 |

- **「誰のためか」は定型で聞く。** 要望の文面には現れないが、何が足りているかの判定を左右する。
  読む人・使う人が誰かによって、同じ成果物の十分さが変わる。
- **「伺いたい点」は選択肢の形で聞く。** 自由記述で聞いてよいのは、お客様しか持っていない事実
  （番号・手順・場所など）だけ。判断を仰ぐときは選択肢と、選んだ場合に何が起きるかを示す。
- 依頼票が確定するまで着手しない。確定とは、お客様が「伺いたい点」に答え、「やらないこと」と
  「完了の判定」に合意した状態を指す。

### 5-2. 納品書

窓口が書く。**依頼票の「完了の判定」の各行に対して**、次の 3 つを埋める。

| 欄 | 書くこと | この欄が守る原則 |
| --- | --- | --- |
| 何をしたか | 実際に行ったこと | — |
| 確認した方法 | どうやって確かめたか | 3-2 |
| **確認していないこと** | その方法では捕まえられないもの | 3-2 |

- **「確認していないこと」が核心の欄である。** 欄名が否定形なので、空欄にすると欠落が見える。
- この書式は、検査範囲より広い主張を**書けなくする**。方法の欄が「名前の一致を見た」なら、
  主張は「名前は一致している」までしか書けない。
- 依頼票に無い項目を納品書に足した場合は、足したことを明示する。範囲外の作業は、黙って
  サービスするのではなく、やったことを申告する。

### 5-3. 工程間の引き継ぎ票

**納品書と同じ書式を、ベンダー内部の引き継ぎにも使う。** お客様の定義を「次工程」に広げるだけで、
同じ仕組みが内側に再帰する（3-7）。

| 欄 | 書くこと |
| --- | --- |
| 渡すもの | 次工程が受け取る成果物 |
| 何をしたか | 自分の工程で行ったこと |
| 確認した方法 | 自分の工程の完了条件を、どうやって確かめたか |
| **確認していないこと** | その方法では捕まえられないもの。**次工程への申し送りになる** |

- **「確認した方法」には手順を書く。** 「確認した」「検証済み」だけでは引き継ぎ票として成立しない。
  次工程は、前工程がどこまで見たかを知らないと、自分がどこから見るべきか決められない。
- **空欄は「全部確かめた」という主張であり、その主張自体が次工程の検査対象になる。**
- 手続きの重さの判定（4 節）は内部の引き継ぎにも効く。即答の層では工程が分かれないので、
  引き継ぎ票は発生しない。

## 6. 手続き

この表は**本件**の経路である。手続きの重さの判定（4 節）は手順 2 の冒頭で行い、
**即答・軽作業の層では、判定に従って手順 2・3・6（書類のやりとり）を飛ばす。**

| 順 | 誰が | 何をする | 動く書類 |
| --- | --- | --- | --- |
| 1 | お客様 | 要望を自分の言葉で言う（曖昧でよい） | — |
| 2 | 窓口 | 聞き取る。依頼票の草案を書く | 依頼票（草案） |
| 3 | お客様 | 伺いたい点に答える。線引きと完了の判定に合意する | 依頼票（確定） |
| 4 | 作る者 | 作る。**渡す前に自分で確かめる**（3-7） | 引き継ぎ票（作る者 → 確かめる者） |
| 5 | 確かめる者 | 正しさを検査する | 引き継ぎ票（確かめる者 → 窓口） |
| 6 | 窓口 | 依頼票と結果を照合し、納品書を書く | 納品書 |
| 7 | お客様 | 完了の判定の一覧を照合して検収する | — |
| 8 | お客様 | 外向きの操作を承認する | — |

### 手続きの分岐

| 状況 | どうするか |
| --- | --- |
| 手順 3 でお客様が線引きに同意しない | 依頼票を手順 2 に戻す。範囲を変えて書き直す |
| 手順 4・5 の途中で、依頼票の前提が崩れたと分かった | **作業を止めて手順 2 に戻す。** 崩れた前提のまま作り続けない |
| 手順 6 で、依頼に答えていない項目が見つかった | 納品書を出さず手順 4 に戻す。お客様に照合を代行させない |
| 手順 7 でお客様が検収しない | 不足を依頼票の追記として受け、手順 4 に戻す |
| 要望が曖昧すぎて依頼票が書けない | 手順 2 で止まる。**推測で埋めて着手しない** |

## 7. 失敗モードと、それを止める仕組み

| 失敗 | 原因 | 止める仕組み |
| --- | --- | --- |
| 要望を取り違えたまま作る | 要約が枠を狭めた | 依頼票「ご要望」の原文引用と「こう理解した」の併記 |
| 検査範囲より広い主張をする | 方法を言わない | 納品書「確認した方法」「確認していないこと」の必須欄 |
| 決定事項が説明に埋もれる | 散文の末尾に置く | 依頼票「伺いたい点」の専用欄。選択肢の形に限定 |
| 範囲外が後から判明する | 線引きの後出し | 依頼票「やらないこと」を着手前に確定 |
| お客様が検収できない | 判定基準が無い | 依頼票「完了の判定」を依頼時に合意 |
| 不足しているのに十分と判断する | 誰のための成果物か不明 | 依頼票「誰のためか」 |
| 崩れた前提のまま作り続ける | 戻る手続きが無い | 手順の分岐表（6 節） |
| 自分の工程の不良を次工程へ流す | 検査役が拾うと期待した | 原則 3-7 と工程間の引き継ぎ票（5-3） |
| 次工程がどこから見るべきか分からない | 前工程が確認範囲を申告しない | 引き継ぎ票の「確認していないこと」（5-3） |

## 8. 限界

モデルで解決できないもの。設計の欠陥ではなく前提である。

1. **お客様が言わなかった制約は分からない。** 情報の非対称であり、原理的に埋まらない。
   依頼票の「誰のためか」が定型で聞くことで一部は拾えるが、全部は拾えない。
2. **好み・体感は代われない。** 「これは好きではない」はお客様にしか言えない。
   完了の判定に好みの項目を入れても、判定そのものはお客様が行う。
3. **外向きの操作の承認は代われない。** 公開・送信・本番反映は、取り返しがつかない範囲に出る操作である。
   ベンダーがお客様の責任範囲に勝手に踏み込まない。
4. **窓口が呼ばれなければ機能しない。** 作業側が窓口を通さずに答えれば、このモデルは成立しない。
   したがって**窓口の起動の引き金は、お客様側にも置く**必要がある。カウンターに来るのはお客様だからである。

## 9. このモデルが要求すること（まとめ）

- お客様に要求するのは 3 つだけ。**要望を言う、依頼票に合意する、検収する。**
- ベンダーに要求するのは 5 つ。**聞き返す、線引きを先に出す、確認の限界を言う、
  依頼と回答を照合する、自分の工程は自分で確かめてから渡す。**
- 仕組みとして置くのは 2 つ。**固定書式の書類と、窓口という役。**
  書類は 3 枚（依頼票・納品書・引き継ぎ票）だが、後の 2 枚は同じ書式である。
  境界を越えるのは前の 2 枚だけで、引き継ぎ票は内側を回る。
