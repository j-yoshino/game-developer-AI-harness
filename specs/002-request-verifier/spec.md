### ご要望(原文)

- 「確かめる者を設計して」
- 「レビュー用エージェントは組み込まれているんだっけ?テストも必要やし、「確かめる者」は確認が必要」
- 「3で」(本件は必ず、軽作業はコードやテストを変えたときだけ検査する)
- 「2で」(納品書の検証と、言語別のレビューを検査する)
- 「案1で進めて」(証拠を必須にし、独立した検査は判断が要る部分に絞る)
- 「案 A: 確かめる者が入れ子で呼ぶ」(言語別のレビューの呼び方)

### こう理解した

作った者とは別の文脈で、作られたものを検査する役(確かめる者)を置く。検査するのは、納品書の主張が完了の判定を満たしているか、納品書の「確認していないこと」に抜けがないか、変更したコードの質(言語・エンジン別のレビュー)。本件の完了前には必ず、軽作業ではコードやテストを変えたときだけ、検査を通す。作る者は、納品書の「確認した方法」にコマンドと出力を貼る。検査の報告は、納品書の末尾に、全文を追記する。

### 誰のためか

このハーネスで開発を頼み、納品書を確認して検収する人(お客様)。作った本人の自己申告だけでは、「確認していないこと」の抜けに、誰も気づけない。独立した検査があれば、検収のとき、抜けや不備を、納品書の中で見られる。

### やらないこと

- 引き継ぎ票。当面使わない。
- 検査役が、コードを修正すること。
- 検査の強制の仕組み(書き込みの遮断など)。第1版では、指示と制限に留める。
- 検査役の書き換えの有無の検査。第1版では、報告に「確認していない」と書く。
- メインによる報告の改変の検知。第1版では、検知しない。
- 窓口の判定や、納品書の承認を、検査役が代わりに行うこと。承認は、ユーザーが行う。

### 完了の判定

- [ ] 本件の完了前に、必ず検査が通り、報告が納品書に追記される(SC-001)。
- [ ] コードやテストを変えた軽作業では検査が通り、ドキュメントだけの軽作業では通らない(SC-002)。
- [ ] 納品書の「確認していないこと」に抜けがあるとき、検査が指摘する(SC-003)。
- [ ] 言語・エンジン別のレビューが検査に含まれ、重大な指摘が報告に残る(SC-004)。
- [ ] 検査の報告が、スタイルだけの指摘で埋まらない(SC-005)。
- [ ] 「確認した方法」に、コマンドと出力が書かれている(SC-006)。
- [ ] 差し戻しが上限を超えても、作業が止まらず、未解決の指摘が報告に載る(SC-007)。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 本件の完了前に、独立した検査が通る (Priority: P1)

ユーザーが新規実装を頼み、作る者が実装を終え、納品書を書く。納品書を「確認待ち」で報告する前に、確かめる者が、別の文脈で検査する。検査の報告は、納品書の末尾の「確かめる者の報告」の節に、全文で追記される。

**Why this priority**: 本件は、取り返しがつかないか、設計に及ぶ依頼である。自己申告だけで納品すると、抜けが残る。

**Independent Test**: 新規実装を1件依頼し、完了前に検査が通り、報告が納品書に追記され、状態が「確認待ち」であることを確認する。

**Acceptance Scenarios**:

1. **Given** 本件の実装が完了した、**When** 納品書を報告しようとする、**Then** 先に確かめる者が検査する。
2. **Given** 確かめる者が報告を返した、**When** 納品書に追記する、**Then** 報告の全文が、「確かめる者の報告」の節に、そのまま載る。
3. **Given** 報告の判定が「承認可」、**When** 報告する、**Then** 納品書は「確認待ち」のまま、ユーザーの承認を待つ。

---

### User Story 2 - 軽作業は、コードを変えたときだけ検査される (Priority: P1)

ユーザーが小さな変更を頼む。作業の差分にソースファイルかテストファイルが含まれるときは、確かめる者が検査する。ドキュメント、rules、設定、HTML だけの変更では、検査を通さず、納品書にその旨と理由を1行で書く。

**Why this priority**: 小さな変更のたびに独立した検査を走らせると、費用が検査の価値を超える。

**Independent Test**: コードを変える軽作業と、ドキュメントだけの軽作業を、1件ずつ依頼し、前者だけで検査が通ることを確認する。

**Acceptance Scenarios**:

1. **Given** 差分に `.cpp` `.hpp` `.cc` `.hh` `.cxx` `.h` `.cs` `.rs` のいずれかが含まれる軽作業、**When** 完了する、**Then** 検査が通る。
2. **Given** 差分が、テストファイル(`tests/` または `Tests/` 配下、名前に `Test` または `_test` を含む)を含む軽作業、**When** 完了する、**Then** 検査が通る。
3. **Given** ドキュメント、rules、設定、HTML だけを変える軽作業、**When** 完了する、**Then** 検査は通らず、納品書に「検査不要: ドキュメントだけの変更」のような1行が書かれる。

---

### User Story 3 - 納品書の抜けが指摘される (Priority: P2)

確かめる者は、納品書の主張を、完了の判定の各項目に照合する。「確認していないこと」に、その項目の主張を、確認方法が捕まえていない抜けがあれば、指摘する。

**Why this priority**: この検査が、自己申告の穴を埋める、本来の目的である。

**Independent Test**: わざと「確認していないこと」に抜けのある納品書を渡し、検査がその抜けを指摘することを確認する。

**Acceptance Scenarios**:

1. **Given** 完了の判定の項目に対し、確認方法が、その項目の主張の一部しか確かめていない納品書、**When** 検査する、**Then** その項目に「確認していないことの抜け」が指摘される。
2. **Given** 完了の判定に直結しない一般的な懸念、**When** 検査する、**Then** 指摘には数えず、「補足」として書かれる。
3. **Given** 納品書の確認方法に、再実行できるコマンドがある、**When** 検査する、**Then** 最も重要なものから最大3つが再実行され、結果が報告される。

---

### User Story 4 - 言語・エンジン別のレビューが、検査に含まれる (Priority: P2)

確かめる者は、変更ファイルの種類に応じて、言語・エンジン別のレビューを呼び、重大な指摘を報告に含める。C++、C#、Rust に加え、Unity と Unreal のレビューがある。

**Why this priority**: レビューが、どの手順にも組み込まれていない、という現状の穴を埋める。

**Independent Test**: 言語ごとに(C++、C#、Rust、Unity、Unreal)変更を用意し、対応するレビューが呼ばれ、CRITICAL と HIGH の指摘が報告に残ることを確認する。

**Acceptance Scenarios**:

1. **Given** Unity のプロジェクトの `Assets/` 配下の `.cs` を変えた、**When** 検査する、**Then** Unity のレビューだけが呼ばれる(汎用の C# のレビューは呼ばれない)。
2. **Given** `Assets/` と `Source/` の両方を変えた、**When** 検査する、**Then** Unity と Unreal の両方のレビューが呼ばれる。
3. **Given** レビュー先がない拡張子(`.py` `.js` `.shader` など)を変えた、**When** 検査する、**Then** 検査は通るが、言語別のレビューは「対象外」と報告される。
4. **Given** レビューが CRITICAL または HIGH の指摘を返した、**When** 報告をまとめる、**Then** その指摘が、そのまま報告に含まれる。

---

### User Story 5 - 差し戻しと、上限を超えたときの扱い (Priority: P3)

報告の判定が「要修正」なら、作る者が直し、納品書を更新して、検査を呼び直す(最大2回)。3回目にも「要修正」が出たら、作業を止めず、未解決の指摘を報告に載せて、「確認待ち」で報告する。「判定不能」は、差し戻しに数えず、そのまま報告する。

**Why this priority**: 無限に差し戻して、作業が終わらなくなることを避ける。

**Independent Test**: 要修正の指摘が残る状況を作り、2回の差し戻しの後、3回目で、作業が止まらず、未解決の指摘付きで報告されることを確認する。

**Acceptance Scenarios**:

1. **Given** 判定が「要修正」、**When** 作る者が直して呼び直す、**Then** 最大2回まで繰り返す。
2. **Given** 3回目にも「要修正」、**When** 報告する、**Then** 未解決の指摘が載ったまま、納品書は「確認待ち」で報告される。
3. **Given** 判定が「判定不能」、**When** 報告する、**Then** 差し戻しには数えず、そのまま報告される。

---

### Edge Cases

- 1つの変更に、複数の言語が混ざっているとき、それぞれのレビューが呼ばれる。
- 検査の報告が長いとき。戻り値の長さの上限は、未検証。CRITICAL と HIGH の指摘を、優先して残す。
- 検査役が、ファイルを書き換えてしまうとき。第1版では、検知しない(報告の「確かめる者が確認していないこと」に書く)。
- メインが、報告を改変して追記するとき。第1版では、検知しない。
- 言語別のレビューを、検査役が呼べないとき(入れ子が動かない)。メインが、検査役とレビューを別々に呼ぶ方式に切り替える。
- 納品書が、証拠(コマンドと出力)を持たないとき。検査は、「確認した方法」の不足として指摘する。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 本件の完了前に、ハーネスは、別の文脈で、独立した検査を必ず行わなければならない。
- **FR-002**: 軽作業では、作業の差分に、ソースファイルまたはテストファイルが含まれるときだけ、検査を行わなければならない。ドキュメント、rules、設定、HTML だけの変更は、対象外とし、納品書にその旨と理由を1行で書かなければならない。
- **FR-003**: 検査の対象を迷うときは、検査する側に倒さなければならない。
- **FR-004**: 作る者は、納品書の「確認した方法」に、コマンドと出力(要点)を書かなければならない。
- **FR-005**: 検査は、ユーザーの原文、依頼票(軽作業は、納品書の「依頼」欄に全文で書いた「こう理解した」と「やらないこと」)、納品書の本文、変更ファイルの一覧を入力としなければならない。
- **FR-006**: 検査は、納品書の主張を、完了の判定の各項目に照合し、「満たす」「満たさない」「判定不能」を、根拠つきで判定しなければならない。
- **FR-007**: 検査は、「確認していないこと」の抜けを指摘しなければならない。対象は、完了の判定の項目に直結する抜け(その項目の主張を、確認方法が捕まえていない場合)だけとする。一般的な懸念は、「補足」として書き、指摘に数えてはならない。
- **FR-008**: 検査は、納品書の確認方法のうち、実行できるコマンドを、最大3つ再実行しなければならない。
- **FR-009**: 検査は、変更ファイルの種類に応じて、言語・エンジン別のレビューを呼ばなければならない。重なるファイルは、特化側(Unity・Unreal)だけを呼ぶ。`Assets/` と `Source/` が混在するときは、両方を呼ぶ。
- **FR-010**: レビュー先がない拡張子は、検査は通し、言語別のレビューを「対象外」と報告しなければならない。
- **FR-011**: 検査は、CRITICAL と HIGH の指摘を、そのまま報告に含めなければならない。スタイルだけの指摘は、報告に含めてはならない。
- **FR-012**: 検査の報告は、判定(承認可・要修正・判定不能)、完了の判定との照合、確認していないことの抜け、再実行の結果、レビューの指摘、確かめる者が確認していないこと(空欄不可。なければ「なし」)を持たなければならない。
- **FR-013**: 検査の報告の全文を、納品書の末尾の「確かめる者の報告」の節に、改変せずに追記しなければならない。
- **FR-014**: 判定が「要修正」のとき、作る者が直し、納品書を更新し、検査を呼び直さなければならない(最大2回)。3回目にも「要修正」なら、作業を止めず、未解決の指摘を載せたまま「確認待ち」で報告しなければならない。「判定不能」は、差し戻しに数えず、そのまま報告しなければならない。
- **FR-015**: 検査役は、ファイルを書き換えてはならない。

### Key Entities *(include if feature involves data)*

- **検査の報告**: 判定、完了の判定との照合、確認していないことの抜け、再実行の結果、レビューの指摘、確かめる者が確認していないこと、を持つ。納品書の末尾に、全文で追記される。
- **納品書(拡張)**: 既存の納品書に、「確認した方法」へのコマンドと出力の記載と、末尾の「確かめる者の報告」の節を足したもの。検査が不要だった場合は、その旨と理由の1行を持つ。
- **検査の対象の判定**: 作業の差分から、検査が必要かを決める。ソースファイルまたはテストファイルを含むか。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 検証用の本件の依頼(3件以上)のすべてで、完了前に検査が通り、報告が納品書に追記される。
- **SC-002**: 検証用の軽作業のうち、コードやテストを変えるもの(3件以上)のすべてで検査が通り、ドキュメントだけのもの(3件以上)のすべてで検査が通らない。
- **SC-003**: わざと抜けを入れた納品書(3件以上)のすべてで、検査が、その抜けを指摘する。
- **SC-004**: 検証用の変更(C++、C#、Rust、Unity、Unreal の各言語につき1件以上)のすべてで、対応するレビューが呼ばれ、CRITICAL と HIGH の指摘が報告に残る。
- **SC-005**: 検査の報告の指摘のうち、スタイルだけの指摘が、0件である。
- **SC-006**: 検証用の納品書のすべてで、「確認した方法」にコマンドと出力が含まれる。
- **SC-007**: 要修正の指摘が残る検証用の依頼で、差し戻しが2回を超えず、3回目に作業が止まらず、未解決の指摘付きで報告される。

## Assumptions

- 第1版では、検査役がファイルを書き換えないことを、指示と制限(書き込み用のツールを持たせない)で担保する。強制はしない。親の権限モードによっては、制限が効かないことがある(確認した事実)。
- 言語別のレビューを、検査役が入れ子で呼べるかは、**未検証**(この環境、Claude Code 2.1.233 で)。動かなければ、メインが別々に呼ぶ方式に切り替える。
- 戻り値の長さの上限は、**未検証**。
- 「`paths` 付きの rules が、サブエージェントでも自動で読み込まれるか」は、**未検証**。Unity と Unreal のレビューが、rules を読む方法は、計画で決める。
- 再実行の上限(3つ)、差し戻しの上限(2回)、モデルの種類は、設計書(`docs/superpowers/specs/2026-11-15-verifier-design.md`)で決めた値である。
- 窓口(spec `001-request-window`)が先に動いていることを前提とする。軽作業の聞き取りと納品書の書式は、窓口の仕組みに従う。
