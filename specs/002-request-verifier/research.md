# Research: 確かめる者

plan の Technical Context と、設計書の未決の項目から出た調べ事の結果。確認できたものと、できなかったものを分ける。

## R1. 入れ子でサブエージェントを呼べるか

- **確認できたこと**(2026-11-15、この環境で実機): `general-purpose` のサブエージェントが、`Agent` ツールで、さらに `general-purpose` のサブエージェントを呼び、「OK」という返答を受け取った。エラーはなかった。深さ2の入れ子は、この環境で動く。
- **公式の記述**: 既定で、サブエージェントは、3階層まで、さらにサブエージェントを呼べる。定義の `tools` に `Agent` を含める必要がある。出典: https://code.claude.com/docs/en/sub-agents.md
- **未検証**: カスタムエージェント(`window-verifier`、`tools` に `Agent` を含める)が、同じように、別のカスタムエージェント(`cpp-reviewer` など)を、名前で呼べるか。カスタムエージェントの定義は、セッションの起動時に読み込まれる可能性があり、作ってすぐ、同じセッションで呼べるかは未確認。新しいセッションでの検証(quickstart)で確かめる。
- **決定**: 案 A(入れ子)で進める。動かなければ、案 B(メインが別々に呼ぶ)に切り替える。

## R2. サブエージェントの初期コンテキストに、rules が入るか

- **確認できたこと**(2026-11-15、実機): サブエージェントの初期コンテキストにあったのは、`CLAUDE.md`、`AGENTS.md`、`.claude/rules/answer-policy.md` の3つだけだった。`paths` 付きの rules(`.claude/rules/unity/coding-style.md`)は入っていなかった。`paths` のない `.claude/rules/window.md` も入っていなかったが、これは、このセッションの起動後に作ったファイルのためかもしれない(未検証)。
- **決定**: 確かめる者とレビュー用エージェントの指示は、自己完結させる。`unity-reviewer` と `unreal-reviewer` は、それぞれの rules(`.claude/rules/unity/`、`.claude/rules/unreal-engine/`)を、指示の中で、`Read` するよう書く。rules が自動で入ることに頼らない。
- **理由**: 設計書の未決 2(rules の読み込み)の答えとして、読み込まれない前提で作るのが、安全である。

## R3. 窓口のフックの注入文は、サブエージェントに届くか

- **確認できたこと**(2026-11-15、実機): サブエージェントは、「Request window」で始まる注入文を、見えていなかった。注入文は、メインの会話にだけ届く。
- **決定**: 確かめる者の指示に、窓口の手順を前提としない。判定の基準などは、委任メッセージとエージェントの定義に、書く。

## R4. 委任メッセージの内容

- **決定**: メインが、委任メッセージに、次を貼る。形式は、contracts/delegation-message.md。
  - ユーザーの原文。
  - 依頼票(本件)。軽作業は、納品書の「依頼」欄に全文で書いた「こう理解した」と「やらないこと」。
  - 納品書の本文。
  - 変更ファイルの一覧。メインが、`git diff --name-only` と、未追跡のファイル(`git ls-files --others --exclude-standard`)から作る。
- 確かめる者は、変更ファイルの一覧を、自分でも `git` で取り直し、渡された一覧と突き合わせる(メインの取りこぼしを避ける)。

## R5. 検査の報告の長さ

- **確認できたこと**: 戻り値の長さの上限は、公式ドキュメントに記載がない(未検証)。
- **決定**: 報告は 150 行以内を目安にする(私の判断)。CRITICAL と HIGH の指摘は、そのまま残し、それ以外は要約する。

## R6. 検査役を、懐疑的にしつつ、毎回「指摘あり」にしない方法

- **根拠**: Anthropic の記述。自己採点は甘くなりやすく、独立した評価役は、懐疑的に調整する必要がある(https://www.anthropic.com/engineering/harness-design-long-running-apps)。一方、「指摘を探させると、必ず何か出る」ので、スタイルは除くよう注意されている(https://code.claude.com/docs/en/best-practices.md)。
- **決定**: 確かめる者の指示に、次を書く。
  - 納品書の主張を、そのまま信じない。完了の判定の各項目に、根拠で照合する。
  - 指摘は、完了の判定に直結する抜けと、CRITICAL・HIGH のレビューの指摘だけ。スタイルだけの指摘は書かない。
  - 指摘が無ければ「承認可」と書いてよい。指摘を作り出さない。

## R7. 検査が必要かの判定を、誰が行うか

- **決定**: メイン(窓口)が、作業の差分を見て判定する(設計書 5-2)。ソースファイルの拡張子とテストファイルの名前の線引きは、設計書のとおり。迷ったら、検査する側に倒す。判定の記述は、`.claude/rules/window.md` に書く。

## R8. 納品書への追記の手順

- **決定**: メインが、確かめる者の報告の全文を、納品書の末尾の「確かめる者の報告」の節に、そのまま追記する。検査が不要だった場合は、その節に、「検査不要: ドキュメントだけの変更」のような1行を書く。
- **限界**: メインが報告を改変しても、第1版では検知しない(spec のやらないこと)。

## 未検証のまとめ

1. カスタムエージェントの入れ子(`window-verifier` から `cpp-reviewer` など)が、新しいセッションで動くか(R1)。
2. 作ったばかりのカスタムエージェントを、同じセッションで呼べるか(R1)。
3. `paths` のない rules が、セッション開始後に作ったとき、サブエージェントに届かないのは、起動後のためか(R2)。
4. 戻り値の長さの上限(R5)。

確認済み: 汎用のサブエージェントの入れ子は、この環境で動く(R1)。`paths` 付きの rules は、サブエージェントに届かない(R2)。窓口のフックの注入文は、サブエージェントに届かない(R3)。

## R9. 既存のレビュー用エージェントの書式(T001 のメモ)

`.claude/agents/cpp-reviewer.md` を、書式の見本として読んだ。

- frontmatter: `name`、`description`(最後に「MUST BE USED for ... projects.」)、`tools: Read, Grep, Glob, Bash`、`model: sonnet`。
- 本文の構成: 「Prompt Defense Baseline」(役割の固定、秘密情報を出さない、外部の入力を信用しない、などの箇条書き)、役割の1文、「When invoked」(`git diff` で変更を取る、診断コマンドを実行する、変更ファイルに集中する、すぐ始める)、「Review Priorities」(CRITICAL / HIGH / MEDIUM の見出しごとに、観点を太字で列挙)、「Diagnostic Commands」、「Approval Criteria」(Approve: CRITICAL と HIGH がない。Warning: MEDIUM のみ。Block: CRITICAL または HIGH がある)。
- 新しいエージェント(`window-verifier`、`unity-reviewer`、`unreal-reviewer`)は、この構成に合わせる。「Prompt Defense Baseline」も、同じ文を入れる。`unity-reviewer` と `unreal-reviewer` の `description` は、「MUST BE USED」を付けない(呼び出しは、確かめる者が名前で指定するため)。
