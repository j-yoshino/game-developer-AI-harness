# Data Model: 窓口

spec の Key Entities を、フィールドと規則に展開する。データベースはなく、すべてファイル上の書式である。

## 依頼の層(Request Tier)

| 値 | 意味 | 手続き |
|---|---|---|
| 質問 | 作業を含まない。ファイルや状態を変えない | `window-question` が答える。依頼票・納品書なし |
| 軽作業 | 取り返しがつき、spec に残さない程度の変更 | brainstorming が聞き取り規模を伝える。メインが作業。納品書あり |
| 本件 | 取り返しがつかない、または分岐が設計に及ぶ。新規実装 | brainstorming → spec(依頼票)→ plan → tasks → implement。納品書あり |

### 判定の規則
- 軸 1: 取り返しがつくか(外に出る操作を含むか)。軸 2: 判断の分岐があるか。
- 迷ったら、層を上げる。
- 層は上げるだけで、下げない。軽作業の途中で、取り返しのつかない操作が必要になったら、本件に上げる(状態遷移: 質問 → 軽作業 → 本件。逆向きはない)。
- 既定の例: ローカルの commit、ドキュメントだけの変更、rules や設定の編集 = 軽作業。push、PR 作成、マージ = 外向きの操作で、本件の確認を取る。

## 依頼票(Request Form)

`spec.md` の先頭の節。新規実装にだけ置く。

| 欄 | 必須 | 規則 |
|---|---|---|
| ご要望(原文) | はい | ユーザーの言葉をそのまま引用する。要約しない |
| こう理解した | はい | 言い換え。原文と並べる |
| 誰のためか | はい | 誰が読む・使う・判断するか |
| やらないこと | はい | 範囲外・できないこと |
| 完了の判定 | はい | チェックボックスの一覧。納品書の各行に対応する |

### 状態
- 草案 → 確定。確定は、ユーザーが「伺いたい点」に答え、やらないことと完了の判定に合意した時点。確定まで、作業に入らない。

## 納品書(Delivery Note)

`docs/納品書/` の Markdown。1依頼につき1ファイル。

| 項目 | 内容 |
|---|---|
| ファイル名 | 新規実装: `<NNN-feature>.md`。軽作業: `<YYYY-MM-DD>-<題名>.md` |
| 状態 | 確認待ち / 承認済み |
| 対象の依頼 | 新規実装: spec へのリンク。軽作業: 「こう理解した」と「やらないこと」 |
| 行(1行 = 完了の判定の1項目) | 3欄(下表) |
| 追加した項目 | 依頼に無い作業を足したときだけ、その旨を書く |

### 行の3欄

| 欄 | 規則 |
|---|---|
| 何をしたか | 実際に行ったこと |
| 確認した方法 | どうやって確かめたか。手順を書く(「確認した」だけは不可) |
| 確認していないこと | その方法では捕まえられないもの。**空欄不可**。なければ「なし」と書く |

### 状態の遷移
- 納品書を置いた時点で、状態は「確認待ち」。ユーザーが承認すると「承認済み」。
- ハーネスは、「確認待ち」の間、完了とは言わない。承認はユーザーが行う。
