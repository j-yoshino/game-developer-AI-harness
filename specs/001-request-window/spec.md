## 依頼票

<!--

  「ご要望」は、ユーザーの言葉をそのまま引用する(要約しない)。

### ご要望(原文)

- 「不具合修正だったり、specに残さない程度のちょっとした変更に対して、窓口が必要」
- 「ただの質問に対しても、窓口が必要やね」
- 「てか、結論窓口は必要」
- 「ユーザーが確認するものになるため、docs以下に納品書を置いて」
- 「軽作業は superpowers で完結できないの?」「メインで作業して納品書だけ足す形で」

### こう理解した

ユーザーのどの発言にも、最初に「窓口」が動く。窓口は、発言を「質問・軽作業・本件」に判定し、種別ごとの手続きに回す。作業の完了後は、ユーザーが確認できる納品書を `docs/納品書/` に残す。新規実装(本件)では、spec の中の依頼票がお客様モデルの依頼票の役を担う。

### 誰のためか

このハーネスを使って開発を頼む人(お客様)。依頼のたびに、聞き返しと報告が決まった形で返ってくることで、取り違えと「確認の限界の言い忘れ」を防ぎたい。納品書を読んで検収するのも、この人である。

### やらないこと

- 「確かめる者」(作った者とは別の文脈で検査する役)の独立した設計。別の設計で扱う。
- 引き継ぎ票。当面使わない。
- 言語・エンジン別のレビュー用エージェントの組み込み。
- メインの会話を専用のエージェントとして動かす方式。
- 第1版では、作った者と納品書を書く者の分離。作った者が納品書も書く(「確認していないこと」は自己申告になる)。

### 完了の判定

- [ ] 質問・軽作業・本件それぞれの発言で、判定が期待どおりに出る(SC-001)。
- [ ] 質問に、依頼票も納品書も出ない。根拠が示される(SC-002)。
- [ ] 軽作業で、`docs/納品書/` に納品書が残る(SC-003)。
- [ ] 新規実装で、spec に依頼票の5欄が埋まり、完了後に納品書が残る(SC-004)。
- [ ] 判定が迷う例で、層が上がる方向にだけ動く(SC-005)。
- [ ] 質問のたびに、会話が重くならない(SC-006)。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 質問に、手続きなしで根拠付きの回答が返る (Priority: P1)

ユーザーが、作業を伴わない質問(「この設定の意味は?」など)をする。窓口は、依頼票も納品書も作らず、質問として答える。回答の根拠は、`path:line`・URL・コマンド出力で示される。

**Why this priority**: 発言のうち、最も多いのは質問だと考えられる。ここで手続きが重いと、ハーネス全体が使われなくなる。

**Independent Test**: 作業を含まない質問を3件入力し、依頼票・納品書・層の宣言が出ず、根拠付きで答えが返ることを確認する。

**Acceptance Scenarios**:

1. **Given** ファイルや状態を変えない質問、**When** ユーザーが発言する、**Then** 依頼票も納品書も作られず、回答に根拠が示される。
2. **Given** 事実として確認できなかった内容を含む質問、**When** 回答する、**Then** 事実でないものは、事実でないと明示される(既存の回答ポリシーのとおり)。

---

### User Story 2 - 軽作業が、納品書付きで終わる (Priority: P1)

ユーザーが、不具合修正や小さな変更(spec に残さない程度)を頼む。窓口は軽作業と判定し、規模を伝え、聞き取る。メインの会話が作業し、完了後に納品書を `docs/納品書/` に書く。納品書は「何をしたか」「確認した方法」「確認していないこと」の3欄を持つ。

**Why this priority**: これまで、新規実装以外の依頼には、通る経路がなかった。

**Independent Test**: 小さな不具合修正を1件依頼し、規模が伝えられ、設計メモや計画に進まず、完了後に納品書が残ることを確認する。

**Acceptance Scenarios**:

1. **Given** 小さな変更の依頼、**When** 窓口が判定する、**Then** 軽作業として規模が伝えられ、設計メモや計画には進まない。
2. **Given** 軽作業が完了した、**When** 納品書が書かれる、**Then** `docs/納品書/<YYYY-MM-DD>-<題名>.md` に、3欄が埋まった状態で置かれ、状態は「確認待ち」になる。
3. **Given** 納品書が「確認待ち」、**When** 報告する、**Then** 完了とは言わず、ユーザーの確認を待つ。

---

### User Story 3 - 新規実装で、依頼票と納品書がそろう (Priority: P2)

ユーザーが新規実装を頼む。窓口は本件と判定し、聞き取りから spec の作成へ進める。spec の中の依頼票の5欄(ご要望の原文、こう理解した、誰のためか、やらないこと、完了の判定)が埋まる。ユーザーが spec に合意するまで、実装に入らない。完了後は、完了の判定の各行に対する納品書が `docs/納品書/<NNN-feature>.md` に残る。

**Why this priority**: お客様モデルの中心の手続きだが、依頼の件数は、質問や軽作業より少ない。

**Independent Test**: 新規実装を1件依頼し、spec に5欄が埋まること、合意前に実装に入らないこと、完了後に納品書が残ることを確認する。

**Acceptance Scenarios**:

1. **Given** 新規実装の依頼、**When** spec が作られる、**Then** 依頼票の5欄が埋まり、ご要望は原文のまま引用される。
2. **Given** 埋まらなかった欄がある、**When** 窓口が確認する、**Then** その欄だけを、選択肢の形で聞く。
3. **Given** ユーザーが spec に合意していない、**When** 作業を始めようとする、**Then** 始めない。
4. **Given** 実装が完了した、**When** 納品書が書かれる、**Then** spec の完了の判定の各行に、「何をしたか」「確認した方法」「確認していないこと」が書かれる。

---

### User Story 4 - 判定が迷うとき、層が上がる (Priority: P2)

判定が迷う発言(外向きの操作を含みそうな依頼など)では、窓口は重い層に倒す。作業中に、取り返しのつかない操作が必要だと分かったときも、層を上げる。層を下げることはしない。

**Why this priority**: 手続きの軽さを守りつつ、取り返しのつかない操作を見逃さないための安全側の既定である。

**Independent Test**: push や PR の作成を含む依頼で、本件の確認が取られることを確認する。

**Acceptance Scenarios**:

1. **Given** push、PR 作成、マージのような外向きの操作を含む依頼、**When** 判定する、**Then** 本件の確認を取る。
2. **Given** 軽作業の途中で、取り返しのつかない操作が必要だと分かった、**When** 判定をやり直す、**Then** 本件に上げ、その旨を伝える。

---

### Edge Cases

- 1つの発言に、質問と作業の依頼が混ざっているとき、作業の層で扱う。
- システムが自分で始めたターン(バックグラウンド完了通知など)でも、窓口の注意が出てしまう。ユーザーの発言とどう区別するかは、未検証(Assumptions を参照)。
- 軽作業と本件の境界にある依頼(複数ファイルにまたがる小さな機能追加など)は、層を上げる側に倒す。
- 納品書に「確認していないこと」が空欄のまま置かれるとき、欠落として見える形でなければならない。
- 窓口の注意に従わなかったとき(判定が出ないなど)。第1版では、強制する手段がない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ハーネスは、ユーザーのどの発言に対しても、最初に依頼の種別(質問・軽作業・本件)を判定しなければならない。
- **FR-002**: 判定は、「取り返しがつくか」と「判断の分岐があるか」の2つの軸で行わなければならない。
- **FR-003**: 判定が迷うとき、ハーネスは重い層に倒さなければならない。一度上げた層を、下げてはならない。
- **FR-004**: 質問に対して、ハーネスは依頼票も納品書も作ってはならない。回答の根拠は、`path:line`・URL・コマンド出力で示さなければならない。
- **FR-005**: 軽作業に対して、ハーネスは規模を伝え、聞き取らなければならない。設計メモや計画には進んではならない。
- **FR-006**: 新規実装に対して、spec は依頼票の5欄(ご要望の原文、こう理解した、誰のためか、やらないこと、完了の判定)を必須の欄として持たなければならない。
- **FR-007**: ご要望は、ユーザーの言葉をそのまま引用しなければならない(要約してはならない)。
- **FR-008**: 依頼票の欄が埋まらないとき、ハーネスは埋まらなかった欄だけを、選択肢の形で聞かなければならない。
- **FR-009**: ユーザーが spec に合意するまで、ハーネスは新規実装の作業に入ってはならない。
- **FR-010**: 軽作業と新規実装の完了後、ハーネスは納品書を `docs/納品書/` に日本語で書かなければならない。新規実装は `<NNN-feature>.md`、軽作業は `<YYYY-MM-DD>-<題名>.md` と名付ける。
- **FR-011**: 納品書は、依頼票の「完了の判定」の各行(軽作業は、聞き取りで確認した「こう理解した」と「やらないこと」)に対して、「何をしたか」「確認した方法」「確認していないこと」を持たなければならない。
- **FR-012**: 納品書は状態(確認待ち・承認済み)を持たなければならない。ハーネスは、納品書を置いたら「確認待ち」と報告し、完了とは言ってはならない。承認はユーザーが行う。
- **FR-013**: 依頼に無い項目を作業に足したとき、納品書にその旨を明示しなければならない。
- **FR-014**: 窓口の手順は、新しいセッションでも、毎回読み込まれなければならない。毎ターン、窓口の注意が短く届かなければならない。

### Key Entities *(include if feature involves data)*

- **依頼の層**: 質問・軽作業・本件のいずれか。2つの軸で決まり、上げることはあっても下げることはない。
- **依頼票**: 新規実装の spec の先頭にある5欄。ユーザーの合意で確定する。
- **納品書**: 作業後の報告。依頼の各項目に対して、3欄と状態を持つ。`docs/納品書/` に1依頼につき1ファイル。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 検証用に用意した発言(質問・軽作業・本件を、各3件以上)のうち、判定が期待どおりに出るものが、全体の90%以上である。
- **SC-002**: 質問の検証用の発言すべてで、依頼票も納品書も作られず、根拠が示される。
- **SC-003**: 軽作業の検証用の依頼すべてで、完了後に納品書が残り、3欄が埋まり、状態が「確認待ち」である。
- **SC-004**: 新規実装の検証用の依頼で、spec の依頼票の5欄が埋まり、完了後に納品書が残る。
- **SC-005**: 判定が迷う検証用の例すべてで、層が上がる方向にだけ動く。
- **SC-006**: 質問の回答の前に、依頼票や層の宣言のような、見える手続きが出ない(0件)。

## Assumptions

- 第1版では、作った者(メインの会話)が納品書も書く。「確認していないこと」は自己申告になる。独立した確認は、別の設計(確かめる者)で扱う。
- 窓口の手順を毎ターン届ける仕組みは、モデルが従うかを保証しない。遵守は、新しいセッションでの実際の挙動で確かめる。従わない場合の対処は、設計書(`docs/superpowers/specs/2026-11-15-window-design.md`)の検証の方針に従う。
- 自分で始めたターンと、ユーザーの発言の区別は、未検証。
- 使用する Claude Code のバージョンは 2.1.233。窓口の注意を毎ターン届ける機能が、このバージョンで動くかは、未検証。
- 設定ファイル `.claude/settings.local.json` は、このリポジトリでコミットする運用である。
- 納品書のフォルダー名とファイル名は、ユーザーの指定(`docs/` 以下)のうえで、設計書で決めた案である。
- 質問に専用の手順を設けることは、ユーザーの要望(「作業無しの質問系は別でスキル欲しい」)である。
