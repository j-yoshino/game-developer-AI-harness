# Research: 窓口

plan の Technical Context と、設計書の未決の項目から出た調べ事の結果。各項目は「決定・理由・検討した他の案」で書く。確認できたものと、できなかったものを分ける。

## R1. UserPromptSubmit フックは、2.1.233 で動くか

- **確認できたこと**: 設定ファイル(`--settings` で渡した JSON)に UserPromptSubmit のフックを書き、`claude -p` で実行したところ、フックのスクリプトが発火した。スクリプトは bash で、Windows の Git Bash で動いた。標準入力に、次の JSON が渡った。
  - `session_id`、`transcript_path`、`cwd`、`prompt_id`、`permission_mode`、`hook_event_name`、`prompt`
- **確認できなかったこと**: `additionalContext` がモデルに届き、従われるか。テスト中、ヘッドレス実行の認証(OAuth)が切れていてモデル呼び出しが失敗したため、検証できていない。
- **決定**: フックは 2.1.233 で使える前提で進める。`additionalContext` の到達と遵守は、タスクで、新しい対話セッションで確かめる(quickstart のシナリオ 1)。
- **検討した他の案**: なし(案 A は設計書で承認済み)。

## R2. 自律ターンとユーザー発言の区別

- **確認できたこと**: 標準入力の JSON に、ユーザー発言か自律ターンかを示すフィールドは、確認できた範囲ではない(R1 の一覧が全て)。公式ドキュメントも、区別方法を記載していない。
- **決定**: スクリプトでは区別しない。注入文に「ユーザーの発言にだけ判定する。システムの通知は対象外」と書き、モデルに任せる。遵守は保証されない。
- **検討した他の案**: `prompt` の文面で通知を判別する。通知の文面は変わりうるため、採らない。

## R3. フックのスクリプトの言語と呼び出し

- **決定**: bash のスクリプト 1 本(`.claude/hooks/window-reminder.sh`)。R1 で、Git Bash から動くことを確認した。
- **呼び出しのパス**: 確認した。フックの実行時、環境変数 `$CLAUDE_PROJECT_DIR` が設定される(値は、Claude を起動したディレクトリ)。command は `bash "$CLAUDE_PROJECT_DIR/.claude/hooks/window-reminder.sh"` とする。リポジトリの外から起動された場合は、そのディレクトリが基準になり、スクリプトが見つからない(その場合、注意が届かないだけで、入力はブロックされない)。
- **検討した他の案**: PowerShell のスクリプト。このリポジトリの spec-kit は `ps` だが、bash を使う他のフックとの整合と、R1 の確認済みの動作を優先した。

## R4. 注入文の長さと言語

- **決定**: 英語で、400 文字以内にする。毎ターン届くため、トークン量を抑える(SC-006)。内容は、「ユーザーの発言ごとに、質問・軽作業・本件を判定する。手順は `window.md`」という指示と、層の概略のみ。
- **理由**: 手順の本体は `window.md` が常時読み込まれるため、注入文は、思い出させる役に徹する。

## R5. spec テンプレートの変更の置き場所

- **確認できたこと**: `.specify/scripts/powershell/common.ps1` の `Resolve-Template` は、テンプレートを次の順で探す。1. `.specify/templates/overrides/`、2. インストール済みの preset、3. extension、4. `.specify/templates/`(core)。
- **決定**: 依頼票の節を足した spec テンプレートを `.specify/templates/overrides/spec-template.md` に置く。core の `.specify/templates/spec-template.md` は変えない。
- **理由**: spec-kit の更新が core を上書きしても、override は残る。設計書の「更新で上書きされうる」という懸念を解消できる。
- **確認できたこと**: `resolve-template.ps1 spec-template` を実行すると、override のテンプレート(依頼票の節を含むもの)が返る。
- **未検証**: `speckit-specify` が、実際にそのテンプレートで spec を作るか(次に `/speckit-specify` を実行したときに確かめる)。
- **検討した他の案**: core を直接編集する。更新で上書きされるため採らない。

## R6. 質問スキルの名前と起動

- **決定**: `window-question`。窓口の rules が、質問と判定したときに、名前で呼ぶと書く。スキルの `description` も、自動起動されうるように書く。
- **理由**: スキルの自動起動は保証されないため、rules に明示する。
- **言語**: 既存のスキル(`check-claude-docs`)に合わせて、日本語で書く。

## R7. 納品書のテンプレートの置き場所

- **決定**: `docs/納品書/_template.md`。先頭が `_` のファイルは、納品書そのものではなく、テンプレートであることを示す。
- **理由**: 納品書は `docs/` 以下に置く、というユーザーの指定。テンプレートも同じ場所にあれば、書式が一か所で見える。

## R8. 納品書の「確認していないこと」を空欄にさせない方法

- **決定**: テンプレートで、その欄に「なし」と書く場合も、「なし」と書くことを必須にする(空欄を許さない)。`window.md` に、「空欄は『全部確かめた』という主張であり、その主張が検査される」と書く(お客様モデル 5-3)。
- **限界**: 検査するのは作った者自身(第1版)。自己申告の限界は、非目標として spec に記載済み。
