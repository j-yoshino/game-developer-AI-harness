# Data Model: 相談役

spec の Key Entities を、欄と規則に展開する。データベースはなく、すべてファイル上の書式である。

## 見方(Viewpoint)

| 番号 | 名前 |
|---|---|
| 1 | 遊びの核 |
| 2 | 遊ぶ人を第一に |
| 3 | 触って磨く |
| 4 | 迷わなさ |
| 5 | 壊れ方・品質・想定外への備え |
| 6 | 世界観・らしさの一貫 |
| 7 | ご褒美と進展の設計 |
| 8 | 時間の速さ |

- 番号と名前は固定。見方が変わるときは、番号を振り直さず、廃止した番号は欠番にし、新しい番号を足す。

## 根拠(Basis)

| 欄 | 規則 |
|---|---|
| 出どころの種類 | `任天堂の記事` / `二次資料の複合結果` / `出典なし(一般論)` のいずれか |
| 強さの印 | `強` / `中` / `弱`。根拠の厚さを表す(発言の正しさではない) |
| 出典 | 任天堂の記事のときだけ、記事の番号・題名・URL。二次資料の複合結果では、個別のソースを書かない。一般論では、書かない |

## 補った点(Added Point)

| 欄 | 規則 |
|---|---|
| 番号 | `A-1`, `A-2`, … 依頼ごとに、1 から振る。却下した番号も、欠番にしない |
| 見方 | 番号と名前(上の表) |
| 内容 | 何を補ったか。1〜2 文 |
| 根拠 | 上の表の 3 欄 |
| 覆したときの影響 | 覆すと、何が変わり、どこまで戻るか。1 文 |
| 状態 | `合意` / `変更` / `却下`。相談役は書かない(ユーザーの応答の後に、メインが付ける) |

## 解釈案(Interpretation)

| 欄 | 規則 |
|---|---|
| 番号 | 案 1〜3 |
| 内容 | 抽象的な依頼を、どう具体的にしたか |
| 推奨 | 3 案のうち 1 つに付ける(案が 1 つのときも付ける) |
| 含む補った点 | 案に含まれる補った点の番号 |

## 状態の遷移

```text
(相談役が返す) 提案 → ユーザーの応答 → 合意 / 変更 / 却下
合意 → (検収で)覆される → 依頼の追記として扱う → 作業に戻る
却下 → 記録に残る(再提案を防ぐ)。全案が却下されたときは、理由を添えて相談役を再び呼ぶ
```

## 完了の判定との対応

- 合意した補った点 1 つにつき、完了の判定の項目を 1 つ足す。
- 体感として合っているか(ユーザーが触って確認する)の項目は、行頭に `[ユーザー検収]` を付ける。確かめる者は、判定の対象外とし、「確かめる者が確認していないこと」に、番号つきで書く。
- 納品書の節は、完了の判定の項目と 1 対 1(補った点ごとの節ができる)。
